# Human Test Checklist: Merge — Two-Way Reconciliation

**Target version:** 0.3.1 (backfill — written after release, alongside the v0.4.0 checklist)
**Ships with commits:** `1fcb83a` (v0.3.0, the merge verb), `84026c8` (v0.3.1, the reference-model fixes)
**Companion automated tests:** 44 in `tests/test_merge.py`, each named for the failure it protects against; 140 total in the suite.

## What this is

`collect` and `apply` are one-way copies. Before 0.3.0, running either on a file that had changed on **both** sides silently discarded one side's work — measured on a real config, a `collect` printed `would copy` and dropped 50 lines that existed only in the checkout. v0.3.0 added `ccs merge` (hand-off to your own diff tool via git's mergetool contract, with a content-survival gate before anything installs) and made `collect`/`apply` **refuse** two-way files. v0.3.1 fixed nine defects that shared one root cause: a comparison against the wrong reference.

The governing invariant, and this checklist's test of every step: **success means validated content survival, never "the tool returned 0."** Three separate silent-loss modes all exited 0 during development.

Anyone can run this; it never touches your real `~/.claude` or `~/claude`.

## Prerequisites

1. `ccs` **0.3.1 or later** (`ccs --version`). On 0.2.x there is no `merge` verb AND no two-way refusal — a one-way verb on a diverged file destroys one side silently. Do not run any two-way scenario on 0.2.x.
2. git on PATH.
3. For Section 4 only: a GUI or terminal diff tool git already knows (`git mergetool --tool-help` lists candidates).

### One-time setup: define the test root

**cmd.exe**: `set TESTROOT=%TEMP%\ccs-merge-checklist`
**PowerShell**: `$TESTROOT = "$env:TEMP\ccs-merge-checklist"`
**POSIX**: `TESTROOT=/tmp/ccs-merge-checklist`

> Blocks below use `$TESTROOT` (verbatim in PowerShell and POSIX; cmd.exe users substitute `%TESTROOT%`). Forward slashes are fine on Windows.

### Build the sandbox (two-commit history, so a true ancestor exists)

Cross-shell (`git` + `python` only). The payload gets **two commits**: the base version, then a checkout-side edit — while the live tree derives from the *base* version with a different edit. That makes the file genuinely two-way divergent with a real common ancestor in history.

```bash
python -c "import os,pathlib; R=os.environ.get('TESTROOT') or r'$TESTROOT'; P=pathlib.Path(R); \
(P/'payload/dotclaude/skills').mkdir(parents=True); \
(P/'live/dotclaude/skills').mkdir(parents=True); \
(P/'payload/dotclaude/skills/alpha.md').write_bytes(b'line A\nline B\nline C\n'); \
(P/'payload/ccs-manifest.json').write_bytes(b'{\"manifest_version\":1,\"territories\":{\"dotclaude\":{\"root_var\":\"CLAUDE_DIR\",\"repo_dir\":\"dotclaude\"}},\"entries\":[{\"repo\":\"dotclaude/skills\",\"territory\":\"dotclaude\",\"target\":\"skills\",\"strategy\":\"copy\"}],\"collect_exclude\":[],\"deny\":[]}'); \
print('sandbox at', R)"
git -C "$TESTROOT/payload" init -q
git -C "$TESTROOT/payload" add -A
git -C "$TESTROOT/payload" -c user.email=t@t -c user.name=t -c commit.gpgsign=false commit -qm base
python -c "import os,pathlib; P=pathlib.Path(os.environ.get('TESTROOT') or r'$TESTROOT'); \
(P/'live/dotclaude/skills/alpha.md').write_bytes(b'line A\nline B\nline C\nline E (live-side)\n'); \
(P/'payload/dotclaude/skills/alpha.md').write_bytes(b'line A\nline B\nline C\nline D (checkout-side)\n')"
git -C "$TESTROOT/payload" add -A
git -C "$TESTROOT/payload" -c user.email=t@t -c user.name=t -c commit.gpgsign=false commit -qm "checkout edit"
```

> The `-c commit.gpgsign=false` matters: a global signing config will otherwise stall these commits on a passphrase prompt.
> `write_bytes` (not `write_text`) is deliberate — on Windows, text mode translates `\n` to `\r\n` and changes what the tool sees.

**Every ccs command below carries the isolation flags** (abbreviated `<FLAGS>`):

```bash
--checkout-dir $TESTROOT/payload --claude-dir $TESTROOT/live/dotclaude --user-claude $TESTROOT/live/userclaude
```

`--user-claude` is load-bearing: merge backups and workspaces default under it. Without the flag they'd land in your real `~/claude`.

## High-Value Verification (~5 minutes)

### HV.1 — The version gate

- [ ] **Steps:** `ccs --version`
- [ ] **Expected:** `0.3.1` or later.
- [ ] **Why this matters:** the pre-merge versions don't refuse two-way files — they overwrite one side and report success. Every other test here assumes the refusal exists.

### HV.2 — Both one-way verbs refuse the two-way file (the founding bug)

- [ ] **Steps:**
  1. `ccs collect <FLAGS> --dry-run`
  2. `ccs apply <FLAGS> --dry-run`
- [ ] **Expected (per design):** both print a `REFUSING` block naming `alpha.md`, pointing to `ccs merge` (and `--force` as the destructive override). Neither reports a successful copy of that file.
- [ ] **KNOWN DEFECT (≤0.4.0, HIGH):** neither refuses — the guard checks `is_file()` on the entry target and skips directory-shaped entries (this sandbox's `skills` entry included), so it has only ever protected single-file entries. On 0.4.0 expect `would copy`/`would apply` for the diverged file with no warning; a real run would silently discard one side. Found in run-03 (2026-08-21); fix targeted at 0.4.1.
- [ ] **Why this matters:** this refusal is the difference between "merge exists" and "merge is optional while data quietly disappears."

### HV.3 — Union merge end-to-end, judged by content survival (not exit code)

- [ ] **Steps:**
  1. `ccs merge <FLAGS> --union --no-launch`
  2. `ccs merge <FLAGS> --union --no-launch --accept`
  3. Inspect the file on **both** sides:
     - **cmd.exe**: `type %TESTROOT%\live\dotclaude\skills\alpha.md` and `type %TESTROOT%\payload\dotclaude\skills\alpha.md`
     - **PowerShell**: `Get-Content $TESTROOT/live/dotclaude/skills/alpha.md; Get-Content $TESTROOT/payload/dotclaude/skills/alpha.md`
     - **POSIX**: `cat $TESTROOT/live/dotclaude/skills/alpha.md $TESTROOT/payload/dotclaude/skills/alpha.md`
- [ ] **Expected:** both copies identical, containing `line D (checkout-side)` **and** `line E (live-side)` — each side's unique content survived. No conflict markers (`<<<<<<<`).
- [ ] **Why this matters:** the invariant itself. A merge that installs while missing either line is the exact failure three different code paths committed during development, all with exit 0.

### HV.4 — Backups of BOTH originals exist before anything was overwritten

- [ ] **Steps:** list the sandbox backup dir:
  - **cmd.exe**: `dir /s /b %TESTROOT%\live\userclaude\backups`
  - **PowerShell**: `Get-ChildItem -Recurse $TESTROOT/live/userclaude/backups | Select-Object FullName`
  - **POSIX**: `find $TESTROOT/live/userclaude/backups -type f`
- [ ] **Expected:** a `ccs-merge` backup area holding **both** pre-merge versions of `alpha.md` (one containing only line D, one containing only line E).
- [ ] **Why this matters:** the backup was once a printed claim with no files behind it — the CLI said "originals backed up" while writing nothing. Check disk, not output.

### HV.5 — The loop closes

- [ ] **Steps:** `ccs status <FLAGS>`
- [ ] **Expected:** `status: clean` (or drift only in entries you have deliberately left divergent). `ccs diff <FLAGS> skills/alpha.md` reports the live/checkout copies identical.
- [ ] **KNOWN DEFECT (≤0.4.0):** plain `ccs diff <path>` crashes with `NameError: _print_file_diff is not defined` (`--difftool` works; only the textual printer is missing). Found 2026-08-21; fix targeted at 0.4.1. On 0.4.0, expect this step to FAIL — record it and move on.

## Section 1: base inference (~5 min)

### 1.1 A true ancestor is found and used

- [ ] **Steps:** rebuild the sandbox, then run `ccs merge <FLAGS> --preview --no-launch` (or plain merge) and read what it reports about the base.
- [ ] **Expected:** the base is the **first commit's** version (lines A,B,C — the genuine common ancestor), not `none` and not the checkout's HEAD. Record the actual wording; the report should let you tell WHICH reference it chose.
- [ ] **Why this matters:** with base=HEAD (a sibling of the truth), the merge machinery "resolves" cleanly and drops content — measured as a 56-line silent loss. Nine of eleven 0.3.x bugs were this shape.

### 1.2 `--base none` forces a two-way

- [ ] **Steps:** `ccs merge <FLAGS> --base none --union --no-launch`
- [ ] **Expected:** still succeeds; result still contains D and E (a 2-way union can't drop either side's additions). The difference from 1.1 is more conflict regions, not lost content.

### 1.3 Live equal to an older commit is ONE-sided drift (regression, found 2026-08-21)

- [ ] **Steps:** rebuild; overwrite live's `alpha.md` with the FIRST commit's exact content (`git -C $TESTROOT/payload show <first-commit>:dotclaude/skills/alpha.md` redirected over the live copy). Live now equals a historical version verbatim; only the checkout has moved. Run `ccs status <FLAGS> --long` and `ccs apply <FLAGS> --dry-run`.
- [ ] **Expected:** status attributes the change to the checkout side only; `apply` offers to copy WITHOUT a two-way refusal. No merge should be demanded.
- [ ] **KNOWN DEFECT (≤0.4.0):** `infer_base` skips any historical candidate equal to either side, so this reports "differs on both sides" and `apply` refuses — measured on a real config as 22 files falsely requiring 22 empty merges. Fix targeted at 0.4.1. On 0.4.0, expect FAIL.

### 1.4 The mirror: checkout unchanged, live deleted lines (regression, same family)

- [ ] **Steps:** rebuild; leave the payload untouched after its LAST commit; set live's `alpha.md` to HEAD's content minus THREE of its lines (a genuine live-side deletion against an unchanged checkout). Run `ccs status <FLAGS> --long` and `ccs collect <FLAGS> --dry-run`.
- [ ] **Expected:** one-sided (live ahead); `collect` copies without refusal.
- [ ] **Why this exists:** the equality-base bug is symmetric, but the phantom-deletion guard measures only base→ours deletions — so a fix accepting "base equals ours" can still spuriously reject "base equals theirs" when live deleted ≥3 lines. This step pins the direction the original fixture misses. On ≤0.4.0, expect FAIL.

## Section 2: the validation gate (~5 min)

### 2.1 Conflict markers block `--accept`

- [ ] **Steps:** rebuild, but make the divergence collide on the SAME line: set live's `alpha.md` to change `line B` → `line B (live)` and the payload HEAD's to `line B (checkout)` (edit + `git commit` the payload side, gpgsign off). Then `ccs merge <FLAGS> --no-launch` (NO `--union`), then `ccs merge <FLAGS> --no-launch --accept`.
- [ ] **Expected:** the workspace result contains `<<<<<<<` markers; `--accept` **refuses to install** it and says why. Nothing on either side is overwritten (verify both files unchanged).
- [ ] **Why this matters:** an unresolved merge that installs is worse than no merge.

### 2.2 A no-op resolution is still a valid merge

- [ ] **Steps:** using the standard sandbox, resolve to something equal to one side: `ccs merge <FLAGS> --no-launch`, overwrite the workspace file with the LIVE side's exact content, then `--accept` (run merge again with `--accept`; it must treat your edited workspace as the resolution — see 2.3).
- [ ] **Expected:** accepted and installed. "The result equals what one side already had" is a legitimate resolution, NOT an error. (The original defect: validation asked "what does it resemble?" instead of "what was lost?")

### 2.3 Re-running merge preserves your edits (resume)

- [ ] **Steps:** `ccs merge <FLAGS> --union --no-launch`; append a marker line of your own to the workspace result file; run the same merge command again; inspect the workspace file.
- [ ] **Expected:** your marker line is still there — the second run resumed from your edited result rather than regenerating a fresh merge over it.
- [ ] **Why this matters:** the original bug regenerated the workspace on every run, destroying a hand-finished resolution.

## Section 3: line endings (~3 min, Windows-relevant)

### 3.1 CRLF live vs LF checkout is not drift and not a wall of conflicts

- [ ] **Steps:** rebuild; rewrite the live file with CRLF endings but identical text to the payload HEAD except one real added line: `python -c "import os,pathlib; pathlib.Path(os.environ.get('TESTROOT') or r'$TESTROOT','live/dotclaude/skills/alpha.md').write_bytes(b'line A\r\nline B\r\nline C\r\nline D (checkout-side)\r\nline F (live)\r\n')"`. Run `ccs status <FLAGS> --long`, then `ccs merge <FLAGS> --union --no-launch --accept`.
- [ ] **Expected:** status reports the one-line difference, not every line; the merge resolves with `line F` surviving, and the conflict count is proportional to real edits. During development, unnormalized EOL produced a 1983-line conflict that normalization reduced to 65 conflicting lines (4%).

## Section 4: the hand-off (MANUAL — requires a real diff tool) (~10 min)

> Skip this section in automated sweeps; it needs eyes and a GUI/terminal tool.

### 4.1 The tool launches with three real panes

- [ ] **Steps:** rebuild; run `ccs merge <FLAGS>` with your configured tool (or `--tool <name>`).
- [ ] **Expected:** the tool opens showing local/base/remote content — actual file contents, **not** files literally named `$LOCAL` or `$REMOTE`. (Historical bug: unexpanded placeholders opened as filenames on Windows, because cmd.exe expands `%VAR%` not `$VAR`.)

### 4.2 Ctrl+C is responsive while the tool is open

- [ ] **Steps:** with the tool still open, press Ctrl+C in the terminal running ccs.
- [ ] **Expected:** ccs aborts promptly (tool may stay open — that's fine); it must NOT queue the interrupt until the tool exits. Nothing installs.

### 4.3 Closing without saving is not a merge

- [ ] **Steps:** relaunch; close the diff tool WITHOUT saving; observe ccs.
- [ ] **Expected:** ccs reports the file as unresolved/unchanged — it must not claim "merged" for an untouched result. Nothing installs.

### 4.4 `ccs diff <path> --difftool` opens the pair

- [ ] **Steps:** `ccs diff <FLAGS> skills/alpha.md --difftool`
- [ ] **Expected:** your diff tool opens live-vs-checkout for that file. Plain `ccs diff <FLAGS> skills/alpha.md` prints the same textually and distinguishes three states: differs / identical / no such file.
- [ ] **KNOWN DEFECT (≤0.4.0):** the plain textual form crashes (`NameError`); only `--difftool` works. See HV.5's note; fix targeted at 0.4.1.

## Section 5: adoption on a second machine (the untested half)

> This section cannot run in a sandbox — it is the script for the first real run on a machine that did NOT author the merged history. Genericized: machine A authored and pushed the payload; machine B pulls it.

- [ ] On machine B: upgrade ccs FIRST and check `ccs --version` (HV.1's rationale, doubled — an old ccs here destroys data).
- [ ] Snapshot machine B's live config (`dz git-snapshot save` or equivalent backup).
- [ ] `git pull` the checkout; `ccs status --long` — record which entries are one-way vs two-way.
- [ ] If two-way: `ccs merge --only <entry> --preview` first; resolve; `ccs diff <path>`; then `--accept`.
- [ ] **The finding to record:** does `--base auto` report a **true ancestor** (machine B's last-synced commit genuinely is one)? If it falls back to sibling/none despite real shared history, that is an `infer_base` defect — capture `git log --oneline` of the payload and file it.
- [ ] `ccs apply --dry-run`, read it, `ccs apply`; then verify per the invariant: spot-check one line unique to each side in the merged file, `ccs status` → clean.
- [ ] Return leg: edit something real, `ccs collect`, commit, push; machine A pulls and reaches `status: clean`.

## What the automated tests DON'T cover

- **A real diff tool** — launch, placeholder expansion, close-without-save, Ctrl+C timing (Section 4; every one of these was a shipped bug first)
- **Real git history as the ancestor source** — fixtures fabricate history; Section 1 uses a genuine two-commit repo, and Section 5 uses two real machines
- **Windows EOL at scale** — the 1983-line-conflict class (Section 3)
- **Backups verified on disk** rather than trusted from output (HV.4)
- **The adoption direction** — never run anywhere as of this writing (Section 5)

## Reporting issues found

1. Note the section/step and exact command with flags.
2. For content-loss findings, attach all three inputs (live, checkout, base) and the produced result — the tuple is what makes it reproducible.
3. Rebuild the sandbox, reproduce once, then file against DazzleML/dazzle-claude-config naming this checklist.
