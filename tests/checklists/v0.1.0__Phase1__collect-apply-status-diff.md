## What this is

Hand-runnable verification of the ccs MVP: syncing Claude Code config between a payload repo checkout and the live `~/.claude` + `~/claude` territories. Run it before tagging v0.1.0, after any refactor of the sync engine, and once per new platform (the POSIX/BSD sections have never been executed at the time of writing). An external tester can run everything using the fixture-based sections; the "real config" section assumes you actually use Claude Code on the box.

## What the A-codes mean

Steps below are tagged with the guarantee they verify. The codes are maintainer shorthand from the design doc; each is spelled out here so this checklist stands on its own:

| Code | The guarantee it verifies |
|---|---|
| **A1** | Secrets are structurally fenced -- a denied filename, or credential-shaped content in any file, is refused by `collect`, and the refusal is reported rather than silent |
| **A2** | `collect` then `apply` is idempotent -- a round trip leaves nothing to do the second time |
| **A3** | Nothing is destroyed -- every overwrite is preceded by a timestamped backup, and removals are staged rather than deleted in place |
| **A4** | ccs never operates on your home directory's own git repository, nor binds to a parent repository from a folder nested inside one |
| **A7** | Exit codes mean what they say: 0 clean, 1 drift or refusals, 2 error |
| **A8** | Files copied into the payload are verified to reach git's index, so an ignore rule cannot silently drop config from the repo |
| **A11** | `apply` refuses to run while the checkout has unresolved merge conflicts |

## Prerequisites

1. Python 3.10+, git, and this repo checked out. Run everything from the repo root.
2. No install needed for most sections: `python -m dazzle_claude_config.cli <verb>`. Section 4 tests the real console scripts via a throwaway venv.
3. **State isolation**: fixture sections use a scratch directory you create; they NEVER touch your real config. Only Section 5 touches the real config, and only with read-only verbs / `--dry-run`.
4. Reset between sections: delete the scratch directory (each section rebuilds it).

## High-Value Verification (~5 minutes)

### HV.1 -- Clean round trip: status is honest

Validates: the shared diff core and exit contract (A2, A7).

- [ ] **Steps:** run `CCS status` on the fresh fixture; then edit `<CCS_FIX>/claude/CLAUDE.md`, run `CCS status` again; then `CCS collect`; then `CCS status` a third time.
- [ ] **Expected:** exit 0 + "status: clean" -> exit 1 + drift line naming `dotclaude/CLAUDE.md` -> collect prints `copied: dotclaude/CLAUDE.md` -> exit 0 clean again.
- [ ] **Why this matters:** if the drift engine or exit codes lie, every other behavior is unverifiable.

### HV.2 -- Planted secret is refused, loudly (A1)

- [ ] **Steps:** create `<CCS_FIX>/claude/agents/leak.md` containing `key = sk-ant-api03-` + 24 letters. Run `CCS collect`; check exit code; confirm the file did NOT appear under `<CCS_FIX>/co/dotclaude/agents/`.
- [ ] **Expected:** a `REFUSED (credential-shaped...)` line naming the file and line number; exit 1; file absent from checkout.
- [ ] **Why this matters:** this is the tool's core promise -- a silent pass here means secrets reach GitHub.

### HV.3 -- Denied filename is refused even though allowlisted (A1)

- [ ] **Steps:** create `<CCS_FIX>/claude/agents/.credentials.json` (any content). `CCS collect`.
- [ ] **Expected:** `REFUSED (deny-list ...)` line; exit 1; not copied.
- [ ] **Why this matters:** the deny-list must beat the allowlist, always.

### HV.4 -- apply backs up before overwriting (A3)

- [ ] **Steps:** edit `<CCS_FIX>/co/dotclaude/CLAUDE.md` to new content; `CCS apply`; read the printed `backups:` path; open the backed-up `CLAUDE.md` inside it.
- [ ] **Expected:** live file has the new content; backup dir contains the PRIOR bytes; exit 0.
- [ ] **Why this matters:** apply without recoverable backups is data loss waiting to happen.

### HV.5 -- The home repo is untouchable (A4)

- [ ] **Steps:** if your home dir is a git repo (csb users): `python -m dazzle_claude_config.cli --checkout-dir <your home dir> status`. Otherwise create a scratch repo, point `--checkout-dir` at a plain SUBDIR of it.
- [ ] **Expected:** clean one-line error (mentions "HOME repo" / "not a git repository root"), exit 2, NO traceback.
- [ ] **Why this matters:** the 2026-04-05 class of incident -- ccs must be structurally unable to touch the home repo.

### HV.6 -- Locked/read-only destination fails gracefully (Windows)

- [ ] **Steps:** make `<CCS_FIX>/claude/CLAUDE.md` read-only (`attrib +r` / `Set-ItemProperty -Name IsReadOnly`); edit the repo copy; `CCS apply`; then clear the read-only bit.
- [ ] **Expected:** `FAILED (...): CLAUDE.md` line; exit 2; NO traceback; other pending files still applied.
- [ ] **Why this matters:** the tester-unbounded run's HIGH finding -- an everyday Windows condition must not crash the tool.

## Section 1: Output & UX quality (~10 min, human judgment)

### 1.1 Readability of each verb

- [ ] **Steps:** run `CCS status`, `CCS diff`, `CCS collect --dry-run`, `CCS apply --dry-run` with a few pending changes staged in the fixture.
- [ ] **Check:** lines are scannable; would-copy vs copied wording is unambiguous; nothing wraps badly at 100-col; no stray ANSI codes; Windows terminal (cp437/1252) renders every character (output is ASCII by design).

### 1.2 Error message quality

- [ ] **Steps:** run with `--checkout-dir` pointing at (a) a missing dir, (b) a dir without a manifest, (c) a manifest with a typo key (hand-edit one in).
- [ ] **Expected:** each produces ONE clear stderr line (`ccs: ...`), exit 2, no traceback, and the message tells you what to fix.

### 1.3 --help discoverability

- [ ] **Steps:** `python -m dazzle_claude_config.cli --help` and each verb's `--help`.
- [ ] **Check:** a newcomer could figure out the collect->push->pull->apply workflow from help text alone; flags are documented; `--version` prints the full build string.

## Section 2: Guard-stack edge cases (~10 min)

### 2.1 Secret smuggled in a .png collects... NOT (fixed in 10e0d49)

- [ ] **Steps:** write a text-content file named `<CCS_FIX>/claude/agents/shot.png` containing an `sk-ant-` token; `CCS collect`.
- [ ] **Expected:** refused; a REAL image file (copy any actual .png in as `icon.png`) still collects without false positives.

### 2.2 A8 -- machine-level git exclude cannot silently eat files

- [ ] **Steps:** append `newbie.md` to `<CCS_FIX>/co/.git/info/exclude`; create `<CCS_FIX>/claude/agents/newbie.md`; `CCS collect`.
- [ ] **Expected:** `ERROR: copied but IGNORED by git (A8...)` naming the file; exit 2.

### 2.3 Type mismatch (dir replaced by file)

- [ ] **Steps:** delete `<CCS_FIX>/claude/agents` (the dir) and create a FILE named `agents` in its place; run `CCS status` and `CCS collect`.
- [ ] **Expected:** `type mismatch` reported; entry skipped; exit 2 on collect; no nested `agents/agents` artifact in the checkout.

### 2.4 Removal semantics

- [ ] **Steps:** create `<CCS_FIX>/claude/agents/local-only.md`; `CCS apply` (expect `removal PENDING`, file untouched, exit 1); then `CCS apply --sync-removals`.
- [ ] **Expected:** file moved under the backup dir's `_removed/` tree -- verify its content survived; exit 0 after.

### 2.5 Conflicted checkout refuses apply (A11)

- [ ] **Steps:** manufacture a merge conflict in the fixture checkout (branch, edit same file both sides, merge); `CCS apply`.
- [ ] **Expected:** `ccs: checkout has unresolved merge conflicts...`, exit 2; `CCS status` prints the MERGE CONFLICTS warning line.

## Section 3: Idempotency & filters (~5 min)

### 3.1 Double collect / double apply

- [ ] **Steps:** stage changes, `CCS collect` twice, then `CCS apply` twice.
- [ ] **Expected:** second run of each prints "nothing to do", exit 0 -- byte-stable.

### 3.2 --only prefix filter + typo warning

- [ ] **Steps:** stage two changes in different entries; `CCS apply --only dotclaude/agents`; then `CCS apply --only bogus/prefix`.
- [ ] **Expected:** first applies ONLY the agents change; second warns `matched no manifest entries`.

## Section 5: Real config on this box (READ-ONLY; ~3 min)

> Skip this section on machines that don't use Claude Code. NOTHING here mutates real state.

### 5.1 Real status / diff / dry-runs

- [ ] **Steps:** with the real payload checkout path: `ccs --checkout-dir <payload>/local status`, then `diff`, `collect --dry-run`, `apply --dry-run`.
- [ ] **Expected:** no tracebacks; statements match your known drift state (clean if you just synced); dry-runs list plausible files ONLY from manifest territories; the deny-list refuses nothing unexpected.
- [ ] **Check:** timing feels instant (<2s on a normal payload). If it doesn't, note it.

### 5.2 First REAL collect/apply round trip (deliberate, once per box)

- [ ] **Steps:** when you are ready to adopt ccs as the real workflow on a box: make a trivial live edit (e.g. add a line to a scratch skill), `ccs collect`, review `git -C <payload>/local diff`, commit/push via git, then on another box `git pull` + `ccs apply --dry-run` + `ccs apply`.
- [ ] **Expected:** the edit arrives on the second box; backups exist there; nothing else changed (`ccs status` clean on both ends).
- [ ] **Why this matters:** this is the product working end-to-end across real machines -- the reason the tool exists.

## What the automated tests DON'T cover

- Real `~/.claude` round trips across actual machines (Section 5.2)
- Windows terminal rendering / codepage behavior of every message
- Console-script entry points from a real pip install (Section 4)
- Files genuinely locked by another process (tests use read-only bits, not open handles -- try locking with an open editor)
- POSIX/BSD anything (Section 6): case-sensitivity, permissions, `python3` vs `python`
- Error message *helpfulness* (a human judgment), --help discoverability
- Performance feel on a payload 10x this size
- Backup dir ergonomics: is `~/claude/backups/ccs/<ts>__apply/` actually navigable when you need it in anger?
