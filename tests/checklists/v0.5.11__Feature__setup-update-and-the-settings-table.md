# Human Test Checklist: `ccs setup update` and the settings table

**Target version:** v0.5.11
**Ships with commit:** `feat: ccs setup update -- your config learns new settings (v0.5.11)`
**Companion automated tests:** 492 total. New here: `tests/test_setup_update.py` (36), `tests/test_config_keys_table.py` (12).

## What this is

A config file used to freeze at the settings of whatever version wrote it. Nothing ever updated it, so a machine could run a new release for weeks while its own config described an older tool. `ccs setup update` closes that.

**This checklist is not run yet, on purpose.** It runs together with `tests/checklists/v0.5.10__Epic__attribution-honesty-deletions-and-the-removal-policy.md`, which was itself written to wait for this work so the whole configuration-and-removal surface verifies in one pass rather than two.

The reason it deserves a human at all is one question no assertion can answer: v0.5.10 shipped a default that **moves files**, and an existing machine's config does not mention it. Section 4 asks a person to judge whether the output makes that discoverable. Everything else here supports that question.

Steps are marked **[agent]** (an automated agent can drive and judge it) or **[eyes]** (needs a person to decide whether something reads clearly or looks right).

**`--explain` is built and shipped in this version.** An earlier revision of this checklist said it was not — that was true when written and false by the time the version shipped, which is precisely the drift this checklist warns about elsewhere. It is covered in Section 6.

## Prerequisites

### P.1 — Confirm what you are testing [agent]

```
ccs --version
```

Must report **0.5.11**.

### P.2 — Build the scratch world [agent]

**Every step runs against a throwaway config directory.** No step may touch your real `~/claude` or `~/.claude`, and no step may touch the production box mounted at `X:`.

Every command below carries `--user-claude <SCRATCH>/user`.

**cmd.exe**:
```cmd
set SCRATCH=%TEMP%\ccs-v0511
rmdir /s /q "%SCRATCH%" 2>nul
mkdir "%SCRATCH%\user"
```

**PowerShell**:
```powershell
$env:SCRATCH = "$env:TEMP\ccs-v0511"
if (Test-Path $env:SCRATCH) { Remove-Item -Recurse -Force $env:SCRATCH }
New-Item -ItemType Directory -Force "$env:SCRATCH\user" | Out-Null
```

**POSIX**:
```bash
export SCRATCH=/tmp/ccs-v0511
rm -rf "$SCRATCH"
mkdir -p "$SCRATCH/user"
```

### P.3 — The stale config fixture [agent]

This is the shape a real second machine actually had — 6 of the 11 settings this version knows. Write it to `<SCRATCH>/user/ccs-config.json`:

```json
{
  "on_divergence": "prompt",
  "difftool": null,
  "interactive": true,
  "status_detail": "auto",
  "status_max_lines": 30,
  "fetch": true
}
```

### P.4 — If any step needs a git fixture [agent]

Most of this checklist does not, but Section 3 optionally puts the config under git to inspect a diff. If you do:

```
git -C <SCRATCH> -c user.email=test@test.invalid -c user.name=ccs-test -c commit.gpgsign=false -c tag.gpgsign=false ...
```

Both parts are required. `-C <scratch>` on every call, never relying on the working directory — a `cd` that silently failed leaves you operating on a real repository. And signing disabled per-invocation, because this machine has `commit.gpgsign = true` globally, so a bare `git commit` fires an **interactive GPG pinentry dialog per commit** at whoever is at the keyboard. A previous checklist omitted that and hit it on its first run. **Never change the global git config to work around it.**

### P.5 — Reset between sections [agent]

Delete `<SCRATCH>/user/ccs-config.json` and re-create the fixture from P.3. Sections are otherwise independent.

## High-Value Verification (~5 minutes)

### HV.1 — A stale config gains exactly what it lacks [agent]

- [ ] **Steps:** with the P.3 fixture in place, run `ccs --user-claude <SCRATCH>/user setup update`
- [ ] **Expected:** five settings added — `ai_merge_command`, `fetch_timeout`, `require_current`, `auto_pull`, `sync_removals`. Exit 0.
- [ ] **Check:** the six original values are unchanged.
- [ ] **Why this matters:** this is the whole feature. Without it, a config describes an older tool than the one running.

### HV.2 — Your keys keep their positions [agent] [eyes]

- [ ] **Steps:** open the file after HV.1.
- [ ] **Expected:** the original six appear **first, in their original order**, with the five new ones appended after.
- [ ] **[eyes]:** does this look like a five-line addition, or like the file was rewritten?
- [ ] **Why this matters:** regenerating produces identical *content*, so no content test can tell the difference. Order is the only observable, and a reordered file turns a small addition into a whole-file diff on something you arranged by hand.

### HV.3 — A second run writes nothing at all [agent]

- [ ] **Steps:** hash the file, run `setup update` again, hash again.
- [ ] **Expected:** identical hash. Output says the config is current. Exit 0.
- [ ] **Why this matters:** "no changes needed" must mean the file was not touched, not that it was rewritten to the same bytes.

### HV.4 — `--dry-run` writes nothing [agent]

- [ ] **Steps:** reset to P.3, hash, run with `--dry-run`, hash again.
- [ ] **Expected:** identical hash; output names each setting it *would* add with its default; says nothing was written.
- [ ] **Why this matters:** a preview that writes is not a preview.

### HV.5 — An unreadable config is never written over [agent]

- [ ] **Steps:** replace the file with `{ "on_divergence": "prompt",,,` — hash it, run `setup update`, hash again.
- [ ] **Expected:** identical hash. Nonzero exit. Says it cannot update and why; the remedy appears on **stderr**.
- [ ] **Why this matters:** a file that will not parse may still hold settings someone cares about. Rewriting it to fix a typo destroys them.

### HV.6 — A new file-touching default is discoverable [eyes]

- [ ] **Steps:** reset to P.3 (which predates `sync_removals`), run `setup update`, read the output as though you had not been told what it does.
- [ ] **Expected:** you can tell that a setting governing file removal now exists and what it is called.
- [ ] **Why this matters:** this is the question the whole feature exists to answer, and the only one a person can judge. See Section 4.

## Section 1: `ccs setup update` — the states (~8 min)

### 1.1 An absent config is created with every setting [agent]
- [ ] Delete the file; run `setup update`.
- [ ] **Expected:** created, containing all 11 settings; exit 0.

### 1.2 A stale config gains exactly the missing ones [agent]
Covered by HV.1. Additionally confirm the count in the summary line matches the number of lines listed above it.

### 1.3 A current config is untouched [agent]
Covered by HV.3. Compare **hashes**, not parsed contents.

### 1.4 A value you set that DIFFERS from the default survives [agent]
- [ ] Set `"status_max_lines": 999` in the fixture; run `setup update`.
- [ ] **Expected:** still 999 afterwards.

### 1.5 A value you set that EQUALS the default survives [agent] [eyes]
- [ ] Set `"fetch": true` explicitly (that *is* the default); run `setup update`.
- [ ] **Expected:** the line is untouched — same position, same formatting.
- [ ] **[eyes]:** compare the before and after text of that line character for character.
- [ ] **Why this is the subtle one:** a key holding the default is indistinguishable from one ccs wrote. Both are yours. "It matches the default so rewriting is harmless" is the reasoning that eventually reformats somebody's whole file.

### 1.6 An unrecognised key is reported and kept [agent]
- [ ] Add `"from_a_future_version": "keep me"` to the fixture; run `setup update`.
- [ ] **Expected:** reported as unknown; **still present and unchanged** afterwards; exit **0**.
- [ ] **Why exit 0:** reporting it is a complete, correct outcome. It usually means a newer ccs wrote this file, and removing it would throw away a setting that version wants back.

### 1.7 An unknown key keeps its position too [agent]
- [ ] Place the unknown key in the *middle* of the file; run `setup update`.
- [ ] **Expected:** it is still in the middle, not moved to the end.

### 1.8 A `_comment` key is not reported as unknown [agent]
- [ ] Add `"_comment": "notes to myself"`; run `setup update`.
- [ ] **Expected:** no "unknown key" line for it — underscore keys are how the sibling record files explain themselves to a reader.

## Section 2: refusing to act (~4 min)

### 2.1 Broken JSON [agent]
Covered by HV.5.

### 2.2 Valid JSON that is not an object [agent]
- [ ] Write `[1, 2, 3]` as the whole file; hash; run `setup update`; hash again.
- [ ] **Expected:** refused, file untouched, nonzero exit.
- [ ] **Why separate from 2.1:** this one **parses cleanly**, so no decode error rescues it accidentally. It is a genuinely different code path, and it was found by mutation testing rather than by anyone thinking of it.

### 2.3 The remedy is on stderr, the status on stdout [agent]
- [ ] Re-run 2.1 with stdout and stderr captured separately.
- [ ] **Expected:** the "cannot update" line on stdout; the what-to-do-about-it line on **stderr**.
- [ ] **Why:** piping the status to a log must not swallow the instruction.

### 2.4 `--dry-run` on an unreadable file [agent]
- [ ] **Expected:** refuses the same way; still writes nothing.

## Section 3: `--dry-run` and the preview (~4 min)

### 3.1 Names every setting with its default [agent]
- [ ] **Expected:** each missing setting listed with the value that will be written (`"untouched"`, `15`, `false`, `null`).

### 3.2 Preview and action agree [agent]
- [ ] Run `--dry-run`, record the settings named; run for real, record the settings added.
- [ ] **Expected:** identical sets. Both read one plan, so they cannot disagree — this test proves that stayed true.

### 3.3 On an absent file [agent]
- [ ] **Expected:** says it would create the file; the file does **not** exist afterwards.

### 3.4 The diff a user would actually see [eyes] — optional
- [ ] Put `<SCRATCH>/user` under git (P.4 rules apply), commit the P.3 fixture, run `setup update`, then `git diff`.
- [ ] **[eyes]:** is this a clean five-line addition?
- [ ] **Why:** this is the guarantee automation cannot check, on the artifact a user would actually look at.

## Section 4: the reason this exists [eyes] (~3 min)

Read this section before running it. v0.5.10 introduced `sync_removals`, whose default **moves files** out of your live config into the backup directory. A machine upgrading from an earlier version has a config that does not mention it.

### 4.1 Discoverability of a new file-touching default [eyes]

- [ ] **Steps:** reset to the P.3 fixture. Run `ccs --user-claude <SCRATCH>/user setup update`. Read only the output.
- [ ] **The question:** you are someone who never set this policy, whose config never mentioned it. **Can you tell that a setting now governs whether files get moved, and what it is called?**
- [ ] If the answer is no, that is a **finding**, and it belongs on #32. Record it against this step with the exact output.
- [ ] **Why this is the most important step here:** every other step in this document can be checked by a machine. This one cannot, and it is the question the feature was built to answer.

### 4.2 Does the summary line tell the truth about scale [eyes]
- [ ] **Expected:** the count in the summary matches the number of settings listed.
- [ ] **[eyes]:** does "nothing you had set was changed" read as reassuring, or as something a tool would say right before changing something you had set?

## Section 5: the settings table (~5 min)

Every setting now carries its default, environment variable, explanation and valid values in one place, with the lookup tables derived from it. Nothing about resolution should have changed — these steps prove that.

### 5.1 Resolution order still holds [agent]
- [ ] With a config setting `status_max_lines` to 50 and `CCS_STATUS_MAX_LINES=77` in the environment, confirm the environment wins.
- [ ] Confirm a per-run flag beats both where one exists.
- [ ] **Why:** the whole environment map is now derived rather than written out literally. A derivation bug would silently disable every override.

  **cmd.exe**: `set CCS_STATUS_MAX_LINES=77`
  **PowerShell**: `$env:CCS_STATUS_MAX_LINES = "77"`
  **POSIX**: `export CCS_STATUS_MAX_LINES=77`

### 5.2 Spot-check several environment variables [agent]
- [ ] `CCS_SYNC_REMOVALS=never`, `CCS_FETCH=0`, `CCS_AUTO_PULL=1` each take effect.
- [ ] **Why not just one:** a derivation that works for one key and not others would pass a single spot-check.

### 5.3 An invalid enum value falls back to the SAFEST value [agent]
- [ ] Set `"sync_removals": "untouced"` (deliberate typo); run any verb.
- [ ] **Expected:** warns that it is not one of the valid values, and uses **`never`** — report only.
- [ ] **Why `never` and not the default:** a typo must never *widen* what the tool deletes. Misspelling it costs a manual step, not a file.

### 5.4 Unset the environment afterwards [agent]
- [ ] **cmd.exe**: `set CCS_STATUS_MAX_LINES=`
- [ ] **PowerShell**: `Remove-Item Env:\CCS_STATUS_MAX_LINES`
- [ ] **POSIX**: `unset CCS_STATUS_MAX_LINES`

## Section 6: `--explain` (~4 min)

The settings table's payoff: the text here is the same string the config machinery reads, so it cannot drift from what it describes.

### 6.1 One setting [agent]
- [ ] `ccs --user-claude <SCRATCH>/user setup update --explain fetch`
- [ ] **Expected:** the name, its default, the explanation, and the environment variable that sets it. Exit 0.

### 6.2 A setting with valid values [agent]
- [ ] `... --explain sync_removals`
- [ ] **Expected:** all three of `untouched`, `all`, `never` listed, plus the explanation of what each does.
- [ ] **Why this one:** it is the file-moving setting, and this is the answer a user gets when they find it in their config and ask what it is.

### 6.3 Every setting at once [agent] [eyes]
- [ ] `... --explain` with no key.
- [ ] **Expected:** all 11 settings.
- [ ] **[eyes] — the real question:** is this a reference you would actually read, or a wall of text? If it needs grouping, paging, or a shorter form, that is a finding. No assertion can judge it.

### 6.4 An unknown setting [agent]
- [ ] `... --explain nonsense`
- [ ] **Expected:** says no such setting, **lists the ones that exist**, exits nonzero.

### 6.5 It writes nothing and needs nothing [agent]
- [ ] With **no config file at all**, `--explain` still works — a new machine can ask before it has anything.
- [ ] No config file is created by asking.

### 6.6 Terminal width [eyes]
- [ ] Run `--explain sync_removals` in a **narrow** pane.
- [ ] **[eyes]:** the text wraps at a fixed 76 columns. Does that read correctly at your actual width, or does it look wrong in a split terminal?

### 6.7 The tool's own advice works [agent]
- [ ] Run `setup update` on a fresh directory; it ends by recommending `ccs setup update --explain <key>`.
- [ ] **Expected:** that exact command works.
- [ ] **Why:** it did not, when a real run first produced that line. The tool was advertising a command it did not have, in a file it had just written to someone's machine.

## What the automated tests DON'T cover

- **A real `~/claude`.** Every test writes into a temporary directory. Only a real run proves nothing escaped into the operator's actual config, and Section 1's location behaviour is only meaningful when the two paths genuinely differ.
- **Whether a diff looks like an addition or a rewrite.** Tests compare parsed contents and key order; a person comparing `git diff` on their own config sees whitespace, formatting and scale. Step 3.4 is the only place that gets checked.
- **Whether a new file-touching default is discoverable.** A test can assert a string appears. It cannot judge whether someone who never set the policy would understand that it now governs their files. That is Section 4, and it is the point of the feature.
- **Terminal rendering.** Colour on a real TTY versus piped, Windows codepage behaviour, wrapping of the longer explanation strings at real widths.
- **POSIX, at all.** Nothing in this surface has ever run on Linux. Path handling, the home-directory default, and file permissions on the written config are all first contact — and the next machine to run this is a Linux VPS.
- **A config being edited while ccs writes it.** No test covers concurrent access; the write is atomic, but that guarantee is untested against a real editor holding the file open (Windows especially).

## Reporting issues found

1. Note the section and step number (e.g. "4.1").
2. Capture the exact command **including `--user-claude`** and the full output, keeping stdout and stderr separate where the step distinguishes them.
3. Keep the scratch config file — it is small, and the actual bytes matter for anything about position or formatting.
4. File against **#32**, referencing this checklist by filename.
5. If a step wrote outside the scratch directory, say so in the title. That is the most serious class here.
