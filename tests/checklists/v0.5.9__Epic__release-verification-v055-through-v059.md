# Human Test Checklist: release verification, v0.5.5 through v0.5.9

**Target version:** v0.5.9
**Ships with commit:** the v0.5.9 release commit (see CHANGELOG `[0.5.9]`)
**Companion automated tests:** 399 tests. Most relevant here: `tests/test_migrate_and_walk.py` (26), `tests/test_remote_ergonomics.py` (32), `tests/test_remote_awareness.py` (15), `tests/test_seed_visibility.py` (14), `tests/test_setup_doctor.py` (14), `tests/test_uncommitted_checkout_guard.py` (9), `tests/test_untracked_attribution.py` (9), `tests/test_dir_seed.py` (7).

## What this is

This is the **release gate** for everything between 0.5.5 and 0.5.9. Unlike previous checklists in this directory, it does not cover one feature -- it covers an accumulated arc of five unreleased versions, because PyPI still serves 0.4.3 and everything since then reaches users in a single publish.

It also has an unusual audience. The next machine to install this release is a **Linux VPS in production**, adopting the tool for the first time. So every step here carries a POSIX note, and the checklist deliberately includes steps a Windows-only run would skip.

Steps are marked **[agent]** or **[eyes]**:

- **[agent]** -- an automated agent can drive this and judge the result, *including* interactive TTY prompts (drive them through `pywinpty` on Windows or a pty on POSIX). A previous checklist in this directory claimed its interactive steps needed a human; a tester agent then drove all of them. Do not repeat that claim.
- **[eyes]** -- genuinely needs a person: judging whether wording is *clear*, whether output is *readable*, whether a design *feels* right. A machine can confirm a string is present; only a person can say it helps.

## Prerequisites

### P.1 -- Know which `ccs` you are testing [agent]

```
ccs --version
pip show dazzle-claude-config
```

The version must report **0.5.9**. If `pip show` reports an `Editable project location`, you are testing that working tree, not an installed artifact -- fine for a pre-release run, but say so in your report.

### P.2 -- Build the scratch world [agent]

**Everything in this checklist runs in a throwaway world.** No step may touch your real `~/.claude` or `~/claude`, and no step may touch the production box mounted at `X:` (read-only, entirely off limits -- do not run even `ccs status` against it).

Every `ccs` invocation below therefore carries all three overrides, written here as `<overrides>`:

```
--checkout-dir <SCRATCH>/co --claude-dir <SCRATCH>/live --user-claude <SCRATCH>/user
```

Create the world:

**cmd.exe**:
```cmd
set SCRATCH=%TEMP%\ccs-v059
rmdir /s /q "%SCRATCH%" 2>nul
mkdir "%SCRATCH%\co\dotclaude\skills"
mkdir "%SCRATCH%\live\skills"
mkdir "%SCRATCH%\user"
```

**PowerShell**:
```powershell
$env:SCRATCH = "$env:TEMP\ccs-v059"
if (Test-Path $env:SCRATCH) { Remove-Item -Recurse -Force $env:SCRATCH }
New-Item -ItemType Directory -Force "$env:SCRATCH\co\dotclaude\skills","$env:SCRATCH\live\skills","$env:SCRATCH\user" | Out-Null
```

**POSIX**:
```bash
export SCRATCH=/tmp/ccs-v059
rm -rf "$SCRATCH"
mkdir -p "$SCRATCH"/co/dotclaude/skills "$SCRATCH"/live/skills "$SCRATCH"/user
```

Then initialise the checkout as a real git repo with **at least two commits**. Base inference deliberately refuses to name a base when only one commit exists, and every file then reads as two-sided -- a one-commit fixture will make half this checklist look broken.

```
git init -q -b main "<SCRATCH>/co"
```

**Every git command in this checklist must carry these overrides:**

```
git -c user.email=test@test.invalid -c user.name=ccs-test -c commit.gpgsign=false -c tag.gpgsign=false ...
```

Without them, a machine with `commit.gpgsign = true` in its global config fires an interactive GPG pinentry dialog **for every fixture commit** -- which blocks an unattended run and interrupts whoever is at the keyboard. The automated suite already does this (`GIT_ID` in `tests/conftest.py`); this checklist must too.

Use per-invocation `-c` only. **Never change the global git config to work around it** -- the operator's signing setup must be exactly as they left it when you finish.

Write `<SCRATCH>/co/ccs-manifest.json`:

```json
{
  "manifest_version": 1,
  "territories": {
    "dotclaude": {"root_var": "CLAUDE_DIR", "repo_dir": "dotclaude"}
  },
  "entries": [
    {"repo": "dotclaude/skills", "territory": "dotclaude", "target": "skills", "strategy": "copy"},
    {"repo": "dotclaude/CLAUDE.md", "territory": "dotclaude", "target": "CLAUDE.md", "strategy": "seed-if-absent"}
  ]
}
```

Create `dotclaude/skills/a.md`, `dotclaude/skills/b.md`, and `dotclaude/CLAUDE.md`; commit as "v0"; change all three; commit as "v1". Copy the v1 contents into `<SCRATCH>/live/` at the matching targets.

### P.3 -- Reset between sections [agent]

Several sections leave the world dirty on purpose. Between sections, either re-run P.2 from scratch (safest, a few seconds), or:

```
git -C <SCRATCH>/co reset --hard -q
git -C <SCRATCH>/co clean -fdq
```

then re-copy live's files.

**Note:** `reset --hard` is acceptable *here only* because this is a throwaway world holding nothing you want. Never use it on a real checkout -- that is exactly the data loss Section 1 exists to prevent.

### P.4 -- POSIX note on line endings [agent]

On Windows the live files will be CRLF while the git index is LF. That is expected and handled: the tool normalizes before comparing ancestry. If you see spurious whole-file differences on POSIX, that is a **finding**, not an expected difference -- report it.

## High-Value Verification (~5 minutes)

If you only have five minutes, run these six. They are the "did this release actually ship" tests.

### HV.1 -- `collect` refuses to destroy uncommitted checkout work [agent]

Validates the single most dangerous bug fixed in this arc (#13, v0.5.8).

- [ ] **Steps:**
  1. Edit `<SCRATCH>/co/dotclaude/skills/a.md` -- add a line. Do not commit.
  2. Edit `<SCRATCH>/live/skills/a.md` differently -- add a different line.
  3. Run `ccs <overrides> collect`
- [ ] **Expected:** output contains `REFUSING`, names `a.md`, says `uncommitted edit`, and names three ways out (`commit it`, `checkout --`, `--force`). Exit code is **nonzero**.
- [ ] **Check:** `<SCRATCH>/co/dotclaude/skills/a.md` still holds YOUR line, not live's.
- [ ] **Why this matters:** before 0.5.8 this silently overwrote your work and exited 0. Hours of payload restructuring could vanish with a success message.

### HV.2 -- the remote leg says WHICH SIDE is ahead [agent] [eyes]

Validates the v0.5.9 wording fix.

- [ ] **Steps:** give the scratch checkout an upstream with a commit it lacks (or one it has that the upstream lacks), then run `ccs <overrides> status`.
- [ ] **Expected:** the `remote` line reads `your checkout is N ahead` or `your checkout is N behind` -- never a bare `N ahead`.
- [ ] **[eyes]:** read the line cold. Can you tell, without thinking, whether you need to push or pull? That was the whole complaint.
- [ ] **Why this matters:** `2 ahead` gave no clue whether the local or the remote side held the extra commits, and the two call for opposite actions.

### HV.3 -- `ccs seed migrate` names a command that exists [agent]

Validates the v0.5.9 rename-completeness fix.

- [ ] **Steps:** make live's `CLAUDE.md` differ from the seed, then run `ccs <overrides> seed migrate` with **no** target.
- [ ] **Expected:** the hint reads `(ccs seed migrate <file> keeps your copy, then proves it)`.
- [ ] **Check:** the string `ccs migrate <file>` -- without `seed` -- appears **nowhere** in the output. Then actually run the command the hint gave you; it must parse and work.
- [ ] **Why this matters:** for one release the tool told users to run a command it had itself removed.

### HV.4 -- `seed migrate` writes backups where the RUN says, not where HOME says [agent]

Validates the v0.5.5 fix, and the highest-consequence step in this document.

- [ ] **Steps:**
  1. Note the current contents of your **real** `~/claude/backups/`, or confirm it does not exist.
  2. Run `ccs <overrides> seed migrate CLAUDE.md` -- with `--user-claude <SCRATCH>/user`.
- [ ] **Expected:** both the kept copy and the apply backup appear **under `<SCRATCH>/user`**.
- [ ] **Check:** your real `~/claude/backups/` is **unchanged**. No new directory, no new file, no new timestamp.
- [ ] **Why this matters:** v0.5.4 wrote six real files into the operator's actual home during a checklist run. See "what mocks don't cover" for why the automated tests could not catch it.

### HV.5 -- a first-contact box can identify itself [agent]

Validates the onboarding path a brand-new machine takes.

- [ ] **Steps:** in a world with **no** `<SCRATCH>/user/ccs-box.json`, run `ccs <overrides> setup box --name testbox --tag scratch`, then `ccs <overrides> doctor`.
- [ ] **Expected:** the box file is created; running `setup box` a second time does **not** overwrite it; `doctor` is read-only and pairs each finding with the command that fixes it.
- [ ] **Why this matters:** this is literally the first thing the VPS will run.

### HV.6 -- `ccs git` passthrough works from anywhere [agent]

- [ ] **Steps:** from a directory that is *not* the checkout, run `ccs <overrides> git log --oneline -3` and `ccs <overrides> git status`.
- [ ] **Expected:** git's real output for the **checkout**, not for whatever repo you are standing in.
- [ ] **Why this matters:** the whole point is never having to `cd` to the payload.

## Section 1 -- v0.5.8: the uncommitted-checkout guard (#13)

~8 minutes.

### 1.1 A modified tracked file is refused [agent]

Covered by HV.1. Confirm the exit code specifically: it must be nonzero, because something you asked for did not happen.

### 1.2 An UNTRACKED checkout file is refused too [agent]

- [ ] **Steps:** create `<SCRATCH>/co/dotclaude/skills/draft.md` and never `git add` it; create a *different* `<SCRATCH>/live/skills/draft.md`; run `collect`.
- [ ] **Expected:** `draft.md` is refused and keeps your content.
- [ ] **Why it is a separate test:** `git diff HEAD` does not report untracked files at all. If the guard had been built on `git diff` instead of `status --porcelain`, this case would silently lose the file.

### 1.3 A STAGED file is refused [agent]

- [ ] **Steps:** edit a checkout file, `git add` it without committing, make live differ, run `collect`.
- [ ] **Expected:** refused. Staged-but-uncommitted work is still work that exists in no commit.

### 1.4 A staged RENAME protects the NEW path [agent]

- [ ] **Steps:** `git -C <SCRATCH>/co mv dotclaude/skills/b.md dotclaude/skills/renamed.md`, then run `collect`.
- [ ] **Expected:** the guard treats `dotclaude/skills/renamed.md` as dirty. It must **not** report the raw porcelain form `old -> new` as if it were a path.
- [ ] **Why this matters:** porcelain reports a rename as `R  old -> new`, and the file `collect` would write is the one on the right. Reorganising a payload -- exactly what the VPS adoption involves -- is mostly renames.

### 1.5 One refusal does not stop the run [agent]

- [ ] **Steps:** make `a.md` dirty in the checkout AND make `b.md` differ only in live. Run `collect`.
- [ ] **Expected:** `b.md` is collected normally; `a.md` is held back. A single protected file must not block everything else.

### 1.6 `--force` overrides, deliberately [agent]

- [ ] **Steps:** repeat 1.1 with `--force`.
- [ ] **Expected:** the checkout file is overwritten with live's content, exit 0. The user asked for it explicitly.

### 1.7 The summary does not claim completeness [agent] [eyes]

- [ ] **Steps:** arrange a run where live matches the checkout everywhere EXCEPT one dirty file, so nothing would be collected anyway. Run `collect`.
- [ ] **Expected:** the summary must not say the checkout "already has everything" while a file was held back.
- [ ] **[eyes]:** does the summary read as honest, or does it bury the refusal?

## Section 2 -- v0.5.5: where backups land

~5 minutes. **This is the section most likely to write outside the scratch world if it regresses.** Run it deliberately.

### 2.1 Location pinning [agent]

Covered by HV.4. Additionally:

- [ ] **Check** the kept copy and the apply backup are in **different** directories. The keep copy lives outside the backup tree on purpose, written by a different code path, so one bug cannot spoil both copies.
- [ ] **Check** the verification step actually ran: the output must state that both copies hash to your pre-migration bytes.

### 2.2 `--dry-run` writes nothing at all [agent]

- [ ] **Steps:** record a directory listing and hashes of `<SCRATCH>/user` and `<SCRATCH>/live`. Run `ccs <overrides> seed migrate CLAUDE.md --dry-run`. Re-record.
- [ ] **Expected:** identical. No backup directory created, no live file touched, exit 0.

### 2.3 POSIX equivalence [agent]

- [ ] On POSIX, repeat 2.1 with `--user-claude` pointed at a scratch path and confirm nothing lands in `$HOME/claude/`. **This has never been run on POSIX** -- the original bug was found on Windows.

## Section 3 -- v0.5.6: attribution for files git has never seen (#29)

~6 minutes.

### 3.1 An uncommitted checkout file APPLIES [agent]

- [ ] **Steps:** create a new file in the checkout, do not commit it, run `apply`.
- [ ] **Expected:** it installs into live. It must **not** be skipped as "an uncommitted local snapshot, older than live" -- git cannot supply a direction for a path with no history, and there is no committed work to protect.
- [ ] **Why this matters:** this is the ordinary author-a-file-in-the-payload loop. It was broken for a release.

### 3.2 `apply` does not claim a match it does not have [agent] [eyes]

- [ ] **Steps:** arrange a run that copies nothing but skips something for direction, or reports a pending removal. Run `apply`.
- [ ] **Expected:** the summary says what was held back rather than asserting "your live config already matches the checkout".
- [ ] **[eyes]:** does the summary contradict anything else in the same output? That was the original tell.

### 3.3 A committed but EMPTY file is not treated as absent [agent]

- [ ] **Steps:** commit a zero-byte file into the checkout; give live a non-empty version; run `status`.
- [ ] **Expected:** it is classified using the commit that exists. `git show HEAD:<path>` succeeds with empty output for an empty tracked file, and emptiness must not be read as absence.
- [ ] **Note:** this was found by mutation testing, not by a person -- the surviving mutant was pointing at a real defect.

## Section 5 -- v0.5.9: remote wording, and the states around it

~6 minutes.

### 5.1 All five remote states [agent] [eyes]

Drive each state and read the line:

| State | Expected line |
|---|---|
| in sync | `main, in sync` |
| local has unpushed commits | `main, your checkout is N ahead -- ccs git push to share` |
| remote has commits you lack | `main, your checkout is N behind -- ccs status --pull` |
| both | `main, your checkout is N ahead and M behind -- diverged; resolve in the checkout (ccs git ...)` |
| auto_pull fast-forwarded | `main, your checkout was N behind -- fast-forwarded` |

- [ ] **[eyes]:** the leg and the run's summary line must not describe the same fact two different ways. Both should read as one story.

### 5.2 Fetch failure is labelled, not guessed [agent]

- [ ] **Steps:** point the checkout at an unreachable remote, run `status`.
- [ ] **Expected:** the line says the pull status is unknown and the fetch failed, gives git's reason, and marks the counts `as last fetched`. It must never assert "in sync" on the strength of a stale tracking ref.
- [ ] **Why this matters:** this exact overclaim was a real bug -- `status` said "in sync with origin/main" when nothing had checked the remote.

### 5.3 `--no-fetch` says so [agent]

- [ ] **Expected:** with `--no-fetch`, in-sync becomes `in sync as last fetched`.

## Section 6 -- cross-cutting surfaces

~8 minutes.

### 6.1 `auto_pull` config [agent]

- [ ] **Steps:** write `{"auto_pull": true}` into `<SCRATCH>/user/ccs-config.json`, put the checkout behind its upstream, run `status`.
- [ ] **Expected:** the checkout is fast-forwarded and the line says so; the verdict afterwards reflects post-pull truth.
- [ ] **Check the refusal path:** make the branch diverge, or leave a dirty file in the way. The fast-forward must be **refused** with git's reason shown verbatim. Nothing may be merged, rebased, or stashed on your behalf.

### 6.2 `ccs status --pull` [agent]

- [ ] **Expected:** does the same thing once, without changing the config.

### 6.3 The seed walk, all four keys [agent]

Drive the TTY through `pywinpty` on Windows or a pty on POSIX. Do **not** mark these as human-only.

- [ ] `k` (keep mine) -- records the decision; the file is not asked about again unless the payload's seed changes.
- [ ] `t` (take the payload's) -- performs the safe migration, keeping your copy first.
- [ ] `d` (diff) -- opens both in the configured diff tool.
- [ ] `q` (quit) -- counts the **current** file as still undecided, not as decided.
- [ ] **Check:** the decision record in `<SCRATCH>/user` is hand-editable JSON, and a malformed file produces a warning plus an empty record -- never a traceback.

### 6.4 `ccs doctor` is genuinely read-only [agent]

- [ ] **Steps:** snapshot the whole scratch world (hashes plus listing), run `doctor`, re-snapshot.
- [ ] **Expected:** identical. A diagnostic that writes is not a diagnostic.

### 6.5 Error paths that must not traceback [agent]

- [ ] Point `--checkout-dir` at a directory that does not exist.
- [ ] Point it at a plain directory nested inside some other git repo.
- [ ] Point it at a directory with no manifest.
- [ ] **Expected in every case:** a clear message naming the problem and, where possible, the fix. **Never** a Python traceback. A nonexistent checkout directory produced a raw traceback in a prior release -- found by a checklist run, not by the suite.

## What the automated tests DON'T cover

- **A fixture that makes two distinct values coincide.** The v0.5.5 backup-root bug is the case study: the tests set `HOME` to the scratch tree, so "derived from HOME" and "derived from the run's territories" produced the *same path*, and the wrong one passed. **A test can only distinguish two things the fixture keeps distinct.** HV.4 exists precisely because a human run, with a real home directory, is the only place the two paths differ.
- **Where files land on a real machine.** Every automated test writes into `tmp_path`. Only a real run can prove nothing escaped into `~/.claude`, `~/claude`, or anywhere else you did not name.
- **Terminal rendering.** Colour on a real TTY versus piped, Windows codepage 437/1252 behaviour, line wrapping at real terminal widths, column alignment in the status tables.
- **Whether the wording actually helps.** A test can assert that `your checkout is 2 ahead` appears in the output. Only a person can say whether the reader now knows what to do -- which is the entire reason 0.5.9 changed it.
- **Real git against a real remote.** Auth prompts, credential helpers, slow or hanging remotes, and whether `GIT_TERMINAL_PROMPT=0` actually prevents a hang rather than merely being set.
- **Real interactive TTY behaviour.** Ctrl-C mid-walk, a diff tool that does not exist, a diff tool that returns nonzero, no TTY at all.
- **POSIX anything.** Every prior checklist in this directory was run on Windows. Exec bits, path separators, case-sensitive filesystems, home-directory semantics, and the CRLF/LF boundary are all first-contact on the VPS.
- **Cross-machine reality.** Two machines, two clocks, two histories, and a push in between. The suite simulates this; it does not experience it.

## Reporting issues found

1. Note the section and step number, e.g. "1.4".
2. Capture the exact command **including all three path overrides** and the full output.
3. Save the scratch world before resetting -- it is small, and reproducible evidence beats a description.
4. File an issue referencing this checklist by filename and the version under test.
5. If the finding is a data-loss risk, say so in the title. Three real bugs in this arc were found this way, not by the suite.
