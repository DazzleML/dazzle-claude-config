# Human Test Checklist: attribution honesty, deliberate deletions, and the removal policy

**Target version:** v0.5.10
**Ships with commit:** TBD (written before the commit; run AFTER the config work in #32 lands)
**Companion automated tests:** 444 total. Added for this work: `tests/test_attribution_honesty.py` (14), `tests/test_sync_removals_policy.py` (15), `tests/test_deleted_on_purpose.py` (9), `tests/test_userconfig_honesty.py` (4).

## What this is

Four defects in the `apply` / `collect` chain, fixed together because they share one root cause: **content alone cannot distinguish "you changed it" from "you never received it."** Every one of them is a place where ccs guessed that question and acted on the guess.

This checklist is deliberately **not** run yet. It waits for the `ccs setup update` work (#32), so the whole configuration-and-removal surface is verified in one pass rather than two. Section 5 exists precisely because this release changes a default in a way an existing box's config file will not mention.

Steps are marked **[agent]** (an automated agent can drive and judge it, interactive prompts included) or **[eyes]** (needs a person to judge whether wording is clear, output is readable, or a design feels right). A machine can confirm a string is present; only a person can say it helps.

## Prerequisites

### P.1 — Know which `ccs` you are testing [agent]

```
ccs --version
pip show dazzle-claude-config
```

Must report **0.5.10**. If `pip show` reports an `Editable project location`, you are testing that working tree rather than an installed artifact — fine, but say so in your report.

### P.2 — Build the scratch world [agent]

**Every step runs in a throwaway world.** No step may touch your real `~/.claude` or `~/claude`, and no step may touch the production box mounted at `X:` (read-only, off limits — do not run even `ccs status` against it).

Every `ccs` call carries all three overrides, written below as `<overrides>`:

```
--checkout-dir <SCRATCH>/co --claude-dir <SCRATCH>/live --user-claude <SCRATCH>/user
```

**cmd.exe**:
```cmd
set SCRATCH=%TEMP%\ccs-v0510
rmdir /s /q "%SCRATCH%" 2>nul
mkdir "%SCRATCH%\co\dotclaude\skills"
mkdir "%SCRATCH%\live\skills"
mkdir "%SCRATCH%\user"
```

**PowerShell**:
```powershell
$env:SCRATCH = "$env:TEMP\ccs-v0510"
if (Test-Path $env:SCRATCH) { Remove-Item -Recurse -Force $env:SCRATCH }
New-Item -ItemType Directory -Force "$env:SCRATCH\co\dotclaude\skills","$env:SCRATCH\live\skills","$env:SCRATCH\user" | Out-Null
```

**POSIX**:
```bash
export SCRATCH=/tmp/ccs-v0510
rm -rf "$SCRATCH"
mkdir -p "$SCRATCH"/co/dotclaude/skills "$SCRATCH"/live/skills "$SCRATCH"/user
```

### P.3 — The git-fixture rule (read this before any `git` command) [agent]

**Every git command in this checklist must carry these overrides:**

```
git -C <SCRATCH>/co -c user.email=test@test.invalid -c user.name=ccs-test -c commit.gpgsign=false -c tag.gpgsign=false ...
```

Two reasons, both learned the hard way:

- **`-C <path>` on every call**, never relying on the working directory. A `cd` that silently failed leaves you operating on a real repository.
- **Signing disabled per-invocation.** This machine has `commit.gpgsign = true` set globally with a real key, so a bare `git commit` fires an interactive GPG pinentry dialog **for every fixture commit** — blocking an unattended run and prompting whoever is at the keyboard to sign something they did not initiate. The previous checklist omitted this and hit it on its first run.

**Never change the global git config to work around it.** Per-invocation `-c` only, so the operator's signing setup is exactly as they left it when you finish.

### P.4 — Seed the fixture [agent]

Write `<SCRATCH>/co/ccs-manifest.json`:

```json
{
  "manifest_version": 1,
  "territories": {
    "dotclaude": {"root_var": "CLAUDE_DIR", "repo_dir": "dotclaude"}
  },
  "entries": [
    {"repo": "dotclaude/skills", "territory": "dotclaude", "target": "skills", "strategy": "copy"}
  ]
}
```

`git init -q -b main`, then build **at least two commits** — base inference deliberately refuses to name a base from a single commit, and every file then reads as two-sided, which makes half this checklist look broken.

### P.5 — Reset between sections [agent]

Re-run P.2/P.4 from scratch (a few seconds, safest), or:

```
git -C <SCRATCH>/co <signing overrides> reset --hard -q
git -C <SCRATCH>/co <signing overrides> clean -fdq
```

`reset --hard` is acceptable **here only** because this world is throwaway. Never on a real checkout — that is the data loss Section 2 exists to prevent.

### P.6 — POSIX note [agent]

On Windows live files are CRLF and the git index is LF; the tool normalizes before comparing. Spurious whole-file differences on POSIX are a **finding**, not an expected difference.

## High-Value Verification (~6 minutes)

### HV.1 — A stale live file is not called "live ahead" [agent]

Validates #36, the defect with the worst consequence.

- [ ] **Steps:**
  1. Commit `s.md` twice, then a third time adding several lines.
  2. Put an **older, never-committed** version in live — one that lacks what HEAD added and adds nothing of its own.
  3. `ccs <overrides> status --long`
- [ ] **Expected:** the file reads `unattributed`, **not** `live ahead`, and the same line shows `0 only live`.
- [ ] **Why this matters:** before this fix, `apply` told you to run `ccs collect` on that file — which would have reverted the committed checkout work.

### HV.2 — `apply` never prints the destructive verb for it [agent]

- [ ] **Steps:** same world, `ccs <overrides> apply`
- [ ] **Expected:** no `ccs collect` hint. The file is **applied** (live was stale, so applying is correct).
- [ ] **Why this matters:** the label being wrong is bad; the *instruction* being wrong is what loses work.

### HV.3 — A proven base is still called "checkout ahead" [agent]

The subtlety that a first version of this fix got wrong.

- [ ] **Steps:**
  1. Commit `s.md` with two rules; commit again with one rule **removed** (an upstream retirement).
  2. Put the **first commit's exact bytes** in live.
  3. `ccs <overrides> status --long`
- [ ] **Expected:** `checkout ahead; live == <sha>` — **not** `unattributed`, even though the line shows `0 only checkout`.
- [ ] **Why this matters:** live byte-equalling a commit is a *proof*, not an estimate. Vetoing here called the most certain case in the tool "direction unproven".

### HV.4 — A file you deleted on purpose stays deleted [agent]

Validates #12.

- [ ] **Steps:**
  1. `ccs <overrides> apply` so live has everything.
  2. Delete one file from live.
  3. `ccs <overrides> apply --keep-deleted skills/<that file>`
  4. `ccs <overrides> apply`
- [ ] **Expected:** the file is **not** restored; output says `left out … you removed this on purpose` and names `--restore-deleted`.
- [ ] **Why this matters:** before this, every sync put it back, with no way to say otherwise.

### HV.5 — A retired file you edited is kept [agent]

Validates #31's narrowing, which matters more than its default.

- [ ] **Steps:**
  1. Retire a file in the checkout (delete + commit).
  2. **Edit** live's copy of it.
  3. `ccs <overrides> apply`
- [ ] **Expected:** the file **survives**, reported as `kept … YOUR copy differs`, naming both `ccs collect` and `--sync-removals`.
- [ ] **Why this matters:** the new default deletes retired files. Deleting one that holds your edits is the failure this project refuses.

### HV.6 — A config saved with a BOM still configures the tool [agent]

- [ ] **Steps:** write `<SCRATCH>/user/ccs-config.json` as UTF-8 **with BOM** containing `{"auto_pull": true}`, then run any verb.
- [ ] **Expected:** `auto_pull` takes effect.
- [ ] **Why this matters:** it previously reverted *every* setting to its default, silently, with the decode error going somewhere nothing printed it.

## Section 1 — #36: attribution honesty (~8 min)

### 1.1 The stale-but-unmatched shape [agent]
Covered by HV.1. Additionally confirm the evidence text names **STALE** as the likelier reading and points at `ccs diff` — the **read-only** verb.

### 1.2 A genuine live edit is still "live ahead" [agent]
- [ ] Live holds a line the checkout lacks → `live ahead`, `1 only live`, and `apply` **does** suggest `ccs collect`.
- [ ] **Why separate:** the veto must not over-correct. Only sides holding nothing unique lose the label.

### 1.3 The proven branch [agent]
Covered by HV.3. Also confirm `apply` still propagates the retirement to live.

### 1.4 Two-sided is untouched [agent]
- [ ] Both sides changed since a shared base → `two-sided` / `both moved`, and `apply` refuses.

### 1.5 The entry rollup never contradicts the file beneath it [agent] [eyes]
- [ ] With one `unattributed` file, the entry line must **not** read `(all one-sided)`.
- [ ] Repeat with a `local snap` file (present both sides, never committed). Same rule.
- [ ] **[eyes]:** read the entry line and the file line together. Do they tell one story?
- [ ] **Why this matters:** the first fix enumerated the kinds it knew about, so an unlisted kind fell straight through into the green claim.

## Section 2 — #12: deliberate deletions (~7 min)

### 2.1 The round trip [agent]
Covered by HV.4. Then `--restore-deleted` and confirm the next `apply` installs it again.

### 2.2 apply reports what it installed into a tree that lacked it [agent] [eyes]
- [ ] A file present in the checkout and absent from live produces a notice naming `--keep-deleted`.
- [ ] An ordinary **modification** produces **no** such notice.
- [ ] **[eyes]:** is the notice informative or noisy on a first apply, where *everything* is absent from live?

### 2.3 The record is hand-editable [agent]
- [ ] `<SCRATCH>/user/ccs-deleted.json` is readable JSON with a `_comment` explaining what it is.
- [ ] Deleting an entry by hand lets the file be installed again.

### 2.4 A malformed record degrades safely [agent]
- [ ] Broken JSON → a **warning**, the sync still runs, no traceback.
- [ ] A record whose `decision` is not `keep-deleted` → flagged `malformed` and the file is **still installed**.
- [ ] **Why this direction matters:** a record store that suppresses on malformed input withholds files you expected to receive.

### 2.5 The summary does not overclaim [agent]
- [ ] With a file held out, the summary must not say `your live config already matches the checkout`.

### 2.6 Location pinning [agent]
- [ ] The record lands under the run's `--user-claude`, **never** your real `~/claude`. Snapshot the real directory before and after and diff it.

## Section 3 — #31: the removal policy (~10 min)

### 3.1 The default and its narrowing [agent]
- [ ] Unmodified retired file → **removed**, message names the reason (`retired upstream, your copy was unmodified`), not the mechanism.
- [ ] Edited retired file → **kept** (HV.5).
- [ ] The kept file's bytes are **exactly** what you wrote.

### 3.2 Removals are recoverable [agent]
- [ ] The removed file exists under `<SCRATCH>/user/backups/ccs/…` with its original content.
- [ ] **Why this matters:** "removed" must always mean "moved to the backup dir", never "destroyed".

### 3.3 A local addition is never staged away [agent]
- [ ] A file that was **never** in the checkout is reported `local only` and left alone.

### 3.4 The other two policies [agent]
- [ ] `"sync_removals": "never"` → reports `PENDING`, stages nothing.
- [ ] `"sync_removals": "all"` → stages even a file you edited.

### 3.5 Both flags override the config [agent]
- [ ] config `never` + `--sync-removals` → stages.
- [ ] config `all` + `--no-sync-removals` → stages nothing.
- [ ] **Why both:** a setting you cannot turn off for one run is a trap.

### 3.6 `CCS_SYNC_REMOVALS` is honoured [agent]

### 3.7 A typo falls back to the SAFEST value [agent]
- [ ] `"sync_removals": "untouced"` → warns `not one of …`, uses **`never`**, stages nothing.
- [ ] **Why not the default:** a typo must never widen what the tool deletes.

### 3.8 The stale-checkout guard, BOTH halves [agent]
- [ ] **Detached:** `git checkout <sha>` then `apply` → `not staging retired files … not on a branch`, nothing staged.
- [ ] **Behind upstream:** give the checkout an upstream one commit ahead, fetch without pulling, then `apply` → `… behind its upstream`, nothing staged.
- [ ] **Explicit override still works:** `--sync-removals` stages even on a detached checkout.
- [ ] **Why this matters:** on a stale tree, everything added since looks retired. The behind-upstream half is the one that fires in ordinary use.

### 3.9 Deny-listed files are structurally unreachable [agent]
- [ ] A denied live file is never staged away under any policy.

### 4.1 BOM tolerance [agent]
Covered by HV.6. Also confirm **every** setting survives, not just the first.

### 4.2 A broken config now warns [agent] [eyes]
- [ ] Malformed `ccs-config.json` → `warning: user config: …`, defaults in effect.
- [ ] **[eyes]:** compare it to the box-config warning printed nearby. Do they read as siblings?
- [ ] **Why this matters:** box-config breakage always warned; user-config breakage did not, so a typo'd config looked identical to an absent one.

### 4.3 A BOM does not mask real syntax errors [agent]
- [ ] BOM **plus** broken JSON → still warns, still falls back.

## Section 5 — the behaviour change that needs eyes (~3 min) [eyes]

**Read this section before running it.** `sync_removals: "untouched"` is a **new default that deletes files** (to the backup dir). An existing box's `ccs-config.json` will not mention the key, because nothing in ccs writes or updates that file.

### 5.1 The upgrade experience [eyes]

- [ ] **Steps:**
  1. Write a `ccs-config.json` containing only the keys an **older** ccs knew (omit `sync_removals`, `auto_pull`, `require_current`, `fetch_timeout`, `ai_merge_command`).
  2. Retire a file in the checkout, leave live's copy unmodified.
  3. `ccs <overrides> apply`
- [ ] **Expected:** the file is removed and the reason is printed.
- [ ] **[eyes] — the actual question:** you are a user who never set this policy and whose config file does not mention it. **From the output alone, can you tell that a policy decided this, what it is called, and how to change it?**
- [ ] If the answer is no, that is a **finding**, and #32 (`ccs setup update` — make an existing config learn new keys) is the real fix. Record it against this step.

## What the automated tests DON'T cover

- **Where files land on a real machine.** Every automated test writes into `tmp_path`. Only a real run proves nothing escaped into `~/.claude`, `~/claude`, or a backup directory you did not name. Sections 2.6 and 3.2 exist for this.
- **Whether a policy is discoverable.** A test can assert that a reason string is printed. Only a person can say whether a user who never set the policy would understand what happened. That is Section 5, and it is the most important [eyes] step here.
- **Terminal rendering.** Colour on a real TTY vs piped, Windows codepage 437/1252, wrapping at real widths, alignment of the status tables.
- **Real git against a real remote.** The behind-upstream guard (3.8) is exercised against a local bare repo in tests; a real remote adds auth, latency, and failure modes.
- **POSIX anything.** Every prior checklist in this directory was run on Windows. Exec bits, path separators, case sensitivity, home-directory semantics, and the CRLF/LF boundary are all first-contact on the VPS.
- **The upgrade path itself.** These tests construct configs directly. Nothing exercises "a box that has been running an older ccs for weeks now upgrades" — which is exactly the situation Section 5 probes.

## Reporting issues found

1. Note the section and step number (e.g. "3.8 behind-upstream half").
2. Capture the exact command **including all three overrides** and the full output.
3. Save the scratch world before resetting — it is small, and reproducible evidence beats a description.
4. File an issue referencing this checklist by filename and the version under test.
5. If the finding is a data-loss risk, say so in the title.
