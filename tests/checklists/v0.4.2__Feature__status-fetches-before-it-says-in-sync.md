# Human Test Checklist: `status` Fetches Before It Says "In Sync"

**Target version:** 0.4.2
**Ships with commit:** `feat: status fetches the upstream before it says "in sync"; the verbs say when the checkout is behind (v0.4.2)`
**Companion automated tests:** 185 total; 15 in `tests/test_remote_awareness.py` (a bare "GitHub" plus two clones, so the upstream really moves). Red-green audited: 13 fail without the change, 2 are invariant guards (the no-upstream wording; "in sync" after a successful fetch, which the old code also said -- without having looked).

## What this is

Until 0.4.2, `ccs status` printed `in sync with origin/main` from `git status -sb`, which compares against whatever the *last* fetch left behind. Nothing in ccs ever fetched. On the first two-machine round trip the line was true only because the operator had run `git fetch` by hand. Now `status` fetches first (remote-tracking refs only), `apply`/`collect` note when the checkout is behind, and a failed fetch produces "pull status unknown" rather than a confident "in sync".

What the automated tests cannot reach: a remote that would **prompt for credentials** (the fetch must fail fast, never hang a read-only verb), **real latency** against GitHub from each of your machines, and the behaviour against a **real** payload repo rather than a bare repo on the same disk.

Anyone can run this. Sections 1-2 use a scratch repo; Section 3 is read-only against your real checkout.

## Prerequisites

1. `ccs --version` shows `0.4.2`.
2. `git` on PATH; for Section 3, a checkout of your real payload with an upstream.
3. Scratch world for Sections 1-2 -- a bare remote, a checkout, and a second clone that plays the other machine. Pick a directory that does not exist yet.

   **cmd.exe**:
   ```cmd
   set W=%TEMP%\ccs042
   git init -q --bare -b main %W%\remote.git
   git clone -q %W%\remote.git %W%\other
   mkdir %W%\other\dotclaude %W%\live %W%\user
   python -c "import json,pathlib,os;w=os.environ['W'];pathlib.Path(w+r'\other\ccs-manifest.json').write_text(json.dumps({'manifest_version':1,'territories':{'dotclaude':{'root_var':'CLAUDE_DIR','repo_dir':'dotclaude'}},'entries':[{'repo':'dotclaude/F.md','territory':'dotclaude','target':'F.md','strategy':'copy'}]}));pathlib.Path(w+r'\other\dotclaude\F.md').write_bytes(b'a\nb\n');pathlib.Path(w+r'\live\F.md').write_bytes(b'a\nb\nc\n')"
   git -C %W%\other add -A && git -C %W%\other commit -qm "seed v0" && python -c "import pathlib,os;pathlib.Path(os.environ['W']+r'\other\dotclaude\F.md').write_bytes(b'a\nb\nc\n')" && git -C %W%\other commit -qam "seed v1" && git -C %W%\other push -q -u origin main
   git clone -q %W%\remote.git %W%\checkout
   set CCS=ccs --checkout-dir %W%\checkout --claude-dir %W%\live --user-claude %W%\user --no-color
   ```

   **PowerShell** (same commands; `$env:W` for `%W%`, and define `function ccs042 { ccs --checkout-dir $env:W\checkout --claude-dir $env:W\live --user-claude $env:W\user --no-color @args }`).

   **POSIX**:
   ```bash
   W=/tmp/ccs042
   git init -q --bare -b main $W/remote.git
   git clone -q $W/remote.git $W/other
   mkdir -p $W/other/dotclaude $W/live $W/user
   ```

   Below, `$CCS` stands for your shell's form. **Reset**: delete the scratch directory and rebuild (`dz safedel` if you have it).

## High-Value Verification (~3 minutes)

### HV.1 -- The other machine pushes; `status` notices without a manual fetch (AC-1)

- [ ] **Steps:** in `other`, append a line to `dotclaude/F.md`, commit, push. Then `$CCS status`.
- [ ] **Expected:** branch line `on main, 1 behind vs origin/main -- git pull` (yellow on a TTY); verdict `status: live matches the checkout -- but the checkout is 1 behind origin/main; git pull then run status again`; exit **1**. The string `in sync` does not appear.
- [ ] **Why this matters:** this is the whole change -- before it, the same command said `in sync`.

### HV.2 -- Unreachable remote: unknown, not "in sync" (AC-2)

- [ ] **Steps:** `git -C $W/checkout remote set-url origin http://127.0.0.1:9/nowhere.git`, then `$CCS status`.
- [ ] **Expected:** `pull status unknown -- fetch failed: <git's reason> (vs origin/main as last fetched)`; verdict `status: clean`; exit 0 (unknown is not drift; live equals the checkout). Restore the URL afterwards: `git -C $W/checkout remote set-url origin $W/remote.git`.

### HV.3 -- `--no-fetch` is honest (AC-3)

- [ ] **Steps:** with a commit still unpulled (HV.1 state), `$CCS status --no-fetch`.
- [ ] **Expected:** `in sync with origin/main as last fetched` if nothing has fetched since the clone -- the stale ref, labelled -- or `1 behind ... as last fetched -- git fetch to confirm` if HV.1's fetch already ran. Either way the words `as last fetched` are present and no network call is made (`GIT_TRACE=1` shows no `fetch` if you want proof).

### HV.4 -- The verbs warn and proceed; `--require-current` refuses (AC-5a/5b)

- [ ] **Steps:** in HV.1's state, edit `$W/live/F.md` (append a line), then `$CCS collect --dry-run`, then `$CCS collect --dry-run --require-current`.
- [ ] **Expected:** first: `note: checkout is 1 behind origin/main -- collecting onto a stale base; git pull before you push`, then `would copy: dotclaude/F.md`, exit 0. Second: `REFUSING: checkout is 1 behind origin/main -- git pull first (--require-current is set)`, exit 1, nothing listed.

## Section 1: Read-only guarantee (AC-4)

- [ ] **Steps:** record `git -C $W/checkout rev-parse HEAD`, `git -C $W/checkout write-tree`, `git -C $W/checkout status --porcelain`, and `git -C $W/checkout rev-parse origin/main`. Put an uncommitted file in the checkout. Run `$CCS status` while `other` has an unpushed-then-pushed commit.
- [ ] **Expected:** HEAD, the index tree, and `status --porcelain` are byte-identical before and after; only `origin/main` moved. Your uncommitted file is untouched.

## Section 2: Failure modes a test cannot construct honestly

### 2.1 A remote that would prompt for credentials fails fast (AC-8) -- MANUAL

- [ ] **Steps:** point the scratch checkout's `origin` at a **private** GitHub repo URL you do not have cached credentials for over HTTPS (or any URL that normally raises a Git Credential Manager window). `$CCS status`.
- [ ] **Expected:** no dialog, no terminal prompt; within the timeout (15 s default) the line reads `pull status unknown -- fetch failed: ...` and the command returns. If a GCM window appears, that is a **FAIL** -- record your git and GCM versions.

### 2.2 Timeout (AC-8) -- MANUAL

- [ ] **Steps:** `git -C $W/checkout remote set-url origin http://10.255.255.1/x.git` (non-routable; connections hang rather than refuse). Set `CCS_FETCH_TIMEOUT=3`. `$CCS status`.
- [ ] **Expected:** returns in ~3 s with `fetch failed: timed out after 3s`. Without the env var, ~15 s.

### 2.3 Latency on a real remote (AC-9) -- MANUAL, record the numbers

- [ ] **Steps:** on each of your machines, against your real payload checkout, time `ccs status` ten times with fetch on, then ten with `--no-fetch`.
- [ ] **Record:** median of each. The difference is the fetch cost. (Reference machine, 2026-08-21: 0.8 s total with fetch, 29-file payload, GitHub over HTTPS.)

## Section 3: Against your real payload (read-only)

- [ ] `ccs status` -- the branch line agrees with `git -C <checkout> fetch && git status -sb`.
- [ ] Push from another machine (or commit + push from a second clone); `ccs status` here says `N behind ... -- git pull` without you fetching. `git pull`; `ccs status` -- back to `in sync` (and the applied/collected files appear in the entries as usual).
- [ ] Turn the network off (or unplug); `ccs status` -- `pull status unknown`, exit code unchanged from the drift state, nothing hangs.

## What the automated tests DO cover

| Area | Test | Count |
|---|---|---|
| behind after a push; in sync only after a fetch; fetch failed -> unknown | `test_remote_awareness.py` | 3 |
| `--no-fetch` / `fetch: false` skip the network and label the line | same | 2 |
| read-only: only `refs/remotes/*` changes | same | 1 |
| apply/collect warn and proceed; `--require-current` and config refuse; failed fetch never refuses | same | 5 |
| no-upstream wording unchanged; timeout reported; non-interactive env; wording states | same | 4 |

## What the automated tests DON'T cover

- A real credential prompt (2.1) and a real stalled connection (2.2)
- Latency against GitHub from each machine (2.3)
- Colour of the behind/unknown lines in a real terminal
- Two remotes, or an upstream on a remote other than `origin` (the code resolves the upstream's remote; not exercised by hand yet)

## Reporting issues found

Note the section, the exact command, and `git -C <checkout> status -sb` plus `git -C <checkout> remote -v` at the time.
