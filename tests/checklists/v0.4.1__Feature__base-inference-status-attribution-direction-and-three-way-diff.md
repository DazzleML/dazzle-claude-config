# Human Test Checklist: Base Inference, Status Attribution, Direction-Aware Verbs, and the Three-Way Diff

**Target version:** 0.4.1
**Ships with commit:** `fix: base inference finds the true ancestor; status shows its evidence; verbs respect direction (v0.4.1)`
**Companion automated tests:** 170 total. Specific to this work: 17 in `tests/test_base_inference.py` (base-inference rules, `ccs diff <path>`, direction skips, status/guard agreement, CRLF cases) and 3 in `tests/test_checklist_v041.py` (written during the first sweep of this checklist: history-walk depth, and the ambiguous-bare-filename refusal). `tests/test_merge.py` (53) covers the two-way guard this builds on. A fresh-context mutation sweep of the new code is recorded in `tests/mutation/v0.4.1__sweep__base-inference.md` (12 mutants: 9 killed, 3 triaged equivalent/don't-care).

## What this is

v0.4.1 fixes how `ccs` decides **which side changed a file**. Before it, `status` said "differs on both sides" for any file that merely differed, and the base-inference behind the two-way guard threw away the strongest evidence it had (a historical commit equal to one side). Measured on a real month of drift: 29 files reported as two-sided, 0 actually were. This release makes the guess honest, shows its evidence, and makes `apply` / `collect` respect direction. It also ships the `ccs diff <path>` printer (which crashed with a `NameError` since 0.3.1) and a three-way view, `--difftool 3`, so a human can look at the base `ccs` chose.

The failure this checklist exists to catch is a **confident wrong attribution**: a label that reads "checkout ahead" when live holds unique work, or a verb that copies the wrong way and exits 0. No exit code reports that; a person comparing the label to the files does.

Anyone can run this. It never touches your real `~/.claude` or `~/claude`; every step runs against a scratch world built by a helper script.

## Prerequisites

1. `ccs` installed from this repo at **0.4.1**: `pip install -e .` from the repo root, then `ccs --version` shows `0.4.1`.
2. `git` on PATH.
3. A merge/diff tool `git` already knows about, for Section 4 only (Beyond Compare, kdiff3, meld, vimdiff, VS Code -- anything `git mergetool --tool-help` lists). Everything else needs no tool.
4. Build the scratch world. Pick a directory that does **not** exist yet; the helper refuses to touch an existing one.

   **cmd.exe**:
   ```cmd
   python tests\checklists\helpers\make_scratch_v041.py %TEMP%\ccs041
   set CCS=ccs --checkout-dir %TEMP%\ccs041\checkout --claude-dir %TEMP%\ccs041\live --user-claude %TEMP%\ccs041\user --no-color
   ```

   **PowerShell**:
   ```powershell
   python tests\checklists\helpers\make_scratch_v041.py $env:TEMP\ccs041
   function ccs041 { ccs --checkout-dir $env:TEMP\ccs041\checkout --claude-dir $env:TEMP\ccs041\live --user-claude $env:TEMP\ccs041\user --no-color @args }
   ```

   **POSIX**:
   ```bash
   python tests/checklists/helpers/make_scratch_v041.py /tmp/ccs041
   CCS="ccs --checkout-dir /tmp/ccs041/checkout --claude-dir /tmp/ccs041/live --user-claude /tmp/ccs041/user --no-color"
   ```

   Below, `%CCS%` (cmd), `ccs041` (PowerShell) and `$CCS` (POSIX) all mean "ccs pointed at the scratch world". Steps are written once with `$CCS`; substitute your shell's form.

5. **Reset between sections**: delete the scratch directory and re-run step 4. Nothing outside it is ever written.

   **cmd.exe**: `rmdir /s /q %TEMP%\ccs041` -- **PowerShell**: `Remove-Item -Recurse -Force $env:TEMP\ccs041` -- **POSIX**: `rm -rf /tmp/ccs041`
   (or `dz safedel <dir>` on a machine that has dazzlecmd, which keeps it recoverable)

### The scratch world, so you can check labels against facts

| File | History | Live | Truth |
|---|---|---|---|
| `CLAUDE.md` | seed, then the checkout added a line | == seed | **checkout ahead** (single-file entry) |
| `s/A.md` | seed, then the checkout added a line | == seed | **checkout ahead** |
| `s/B.md` | seed only | seed + a local line | **live ahead** |
| `t/C.md` | seed, then the checkout edited line 2 | seed with line 4 edited | **two-sided** |
| `s/D.md` | never committed (uncommitted file in the checkout) | a newer version | **local snapshot** |
| `s/E.md` | seed, then the checkout added a line | == seed, **CRLF** line endings | **checkout ahead** |
| `s/F.md` | seed only | == seed, **CRLF** | identical (must not be listed) |
| `s/emoji.md` | seed only | seed + a character outside cp1252 | **live ahead** |

## High-Value Verification (~5 minutes)

**If you only have 5 minutes**, run these five. They are the "did the work actually ship" tests.

### HV.1 -- Every label matches the truth table

Validates: `_classify` attributes through the same base inference the guard uses; one-sided files are never called two-sided.

- [ ] **Steps:**
  ```
  $CCS status --long
  ```
- [ ] **Expected** (shas will differ; structure will not):
  ```
  differences in 3 entries:
    dotclaude/CLAUDE.md: differs -- one-sided (checkout ahead; live == <sha>) -- ...
    dotclaude/s: 5 files differ (all one-sided) -- ...
        one-sided   A.md      ...  -- checkout ahead; live == <sha>
        one-sided   B.md      ...  -- live ahead; checkout == <sha>
        local snap  D.md      ...  -- never committed -- the checkout copy is a local snapshot; collect replaces it
        one-sided   E.md      ...  -- checkout ahead; live == <sha>
        one-sided   emoji.md  ...  -- live ahead; checkout == <sha>
    dotclaude/t: 1 file differs (1 on both sides) -- ...
        two-sided   C.md  ...  -- both moved since <sha>

  status: drift in 3 entries -- 1 file differs on BOTH sides; run ccs merge for those (collect/apply would overwrite one side; --long shows which and why)
          one-sided drift is safe with ccs collect (live -> checkout) or ccs apply (checkout -> live)
  ```
  Exit code 1. `F.md` is **absent** (CRLF-vs-LF is not a difference). The `<sha>` after `live ==` is the **seed** commit for A, E and CLAUDE.md; the one after `checkout ==` is the seed for B and emoji (run `git -C <scratch>/checkout log --oneline` to compare).
- [ ] **Why this matters:** this exact table is what was wrong before -- every one of these read "both sides".

### HV.2 -- `apply` skips what live is ahead on, and says why

Validates: direction-aware `apply`; the two-way gate still refuses unscoped.

- [ ] **Steps:**
  ```
  $CCS apply --dry-run
  $CCS apply --only dotclaude/s --dry-run
  ```
- [ ] **Expected:** the first **refuses** (`REFUSING: 1 file changed on BOTH sides ... t/C.md`), exit 1 -- the two-way gate is unchanged. The second, scoped away from `t`:
  ```
  skipped s/B.md -- live is ahead -- nothing to apply; `ccs collect` it
  skipped s/D.md -- checkout copy is an uncommitted local snapshot, older than live
  skipped s/emoji.md -- live is ahead -- nothing to apply; `ccs collect` it
  would apply: s/A.md
  would apply: s/E.md
  ```
  exit 0.
- [ ] **Why this matters:** before 0.4.1, `apply` would have reverted B and emoji to the checkout's older content and reported success.

### HV.3 -- `collect` skips what the checkout is ahead on

- [ ] **Steps:**
  ```
  $CCS collect --only dotclaude/s --dry-run
  ```
- [ ] **Expected:**
  ```
  skipped dotclaude/s/A.md -- checkout is ahead -- nothing to collect; `ccs apply` it
  skipped dotclaude/s/E.md -- checkout is ahead -- nothing to collect; `ccs apply` it
  would copy: dotclaude/s/B.md
  would copy: dotclaude/s/D.md
  would copy: dotclaude/s/emoji.md
  ```
  exit 0. `D.md` is copied: the checkout's copy is a stale uncommitted snapshot and live is newer.
- [ ] **Why this matters:** the mirror of HV.2 -- `collect` would have undone the other machine's A and E.

### HV.4 -- `ccs diff <path>` has three distinct outcomes

- [ ] **Steps:**
  ```
  $CCS diff s/A.md
  $CCS diff s/F.md
  $CCS diff s/nope.md
  ```
- [ ] **Expected:** a unified diff with `-a4 (from the other machine)` in red, exit **1**; `identical -- live and the checkout agree: live/s/F.md`, exit **0** (CRLF vs LF normalised); `no such file in any manifest entry: 's/nope.md' -- run ccs diff with no argument to list what differs` on stderr, exit **2**.
- [ ] **Why this matters:** until 0.4.1 this command raised `NameError` on every call.

### HV.5 -- The three-way view refuses without a console, opens with one

- [ ] **Steps** (first from a terminal, then with stdin redirected):
  ```
  $CCS diff s/A.md --difftool 3
  ```
  **cmd.exe**: `%CCS% diff s/A.md --difftool 3 < NUL` -- **PowerShell** (no input redirection operator; go through cmd): `cmd /c "ccs --checkout-dir %TEMP%\ccs041\checkout --claude-dir %TEMP%\ccs041\live --user-claude %TEMP%\ccs041\user --no-color diff s/A.md --difftool 3 < NUL"` -- **POSIX**: `$CCS diff s/A.md --difftool 3 </dev/null`
- [ ] **Expected:** from a terminal, your mergetool opens **three panes** -- live on the left, the inferred base in the middle (a file named `dotclaude__s__A.md.base-<sha>` under `<scratch>/user/merge/ccs/look/`), the checkout on the right -- and the console prints `opened <tool> (3-way): live | base <sha> == live (checkout ahead) | checkout/dotclaude/s/A.md` followed by `output pane is a scratch copy (...look-only); nothing is written back`. Redirected: `ccs: no console attached -- refusing to launch an interactive merge tool`, exit 3, nothing opens.
- [ ] **Why this matters:** this is the only place a human can see the base `ccs` reasoned from. **Never run from a real TTY before this checklist** -- if the panes are wrong, the whole attribution story is unverifiable by eye.

## Section 1: Status labels in detail (~5 min)

### 1.1 The single-file entry carries its evidence inline

- [ ] **Steps:** `$CCS status --long`, read the `dotclaude/CLAUDE.md` line.
- [ ] **Expected:** `differs -- one-sided (checkout ahead; live == <sha>)` on the entry line itself (single-file entries have no per-file breakdown, so the evidence rides there). Not `differs -- both sides`.

### 1.2 Short form says less, never different

- [ ] **Steps:** `$CCS status` (no `--long`), and compare with `--long`.
- [ ] **Expected:** on this small scratch world the two outputs are **byte-identical** -- the short form collapses the per-file rows only when they would exceed its line budget (`status_detail` defaults to `auto`), and 8 files never reach it. That is correct; what this step checks is that nothing *else* differs (entry lines, verdict, exit code). To see the collapse itself, run both forms against a real payload with more than a couple of dozen differing files (Section 5): `--long` shows the per-file rows, the short form shows only the entry lines, and the verdict is the same in both.

### 1.3 Colour rendering (Windows console + a POSIX terminal)

- [ ] **Steps:** run `status --long` **without** `--no-color` in cmd.exe or Windows Terminal, and in any POSIX terminal.
- [ ] **Expected:** `one-sided` green, `two-sided` magenta, `local snap` yellow, evidence dim. Columns stay aligned (the label column is padded to the widest label). No stray escape codes in cmd.exe's legacy console.
- [ ] **Check:** pipe it -- `... status --long | more` (cmd) / `| Select-Object -First 20` (PowerShell) / `| cat` (POSIX) -- and confirm the codes disappear when not on a TTY.

### 1.4 A CRLF live file is attributed, not mislabelled

- [ ] **Steps:** read the `E.md` row from HV.1.
- [ ] **Expected:** `one-sided ... checkout ahead; live == <seed sha>`, same as `A.md`. (Mutation M9 in the sweep report is the regression this guards.)

### 1.5 Two-sided count is real, not "everything that differs"

- [ ] **Steps:** in the scratch live tree, overwrite `t/C.md` with the checkout's copy, then `$CCS status --long`.

  **cmd.exe**: `copy /y %TEMP%\ccs041\checkout\dotclaude\t\C.md %TEMP%\ccs041\live\t\C.md` -- **PowerShell**: `Copy-Item $env:TEMP\ccs041\checkout\dotclaude\t\C.md $env:TEMP\ccs041\live\t\C.md -Force` -- **POSIX**: `cp /tmp/ccs041/checkout/dotclaude/t/C.md /tmp/ccs041/live/t/C.md`
- [ ] **Expected:** `dotclaude/t` disappears from the list; the verdict line changes to the no-two-sided form (`status: drift in 2 entries` with **no** "BOTH sides" clause); `apply --dry-run` without `--only` now proceeds and prints the HV.2 skips.
- [ ] Reset (Prerequisites step 5) before continuing.

## Section 2: The verbs, for real (~5 min)

Everything above was `--dry-run`. The real copy must match it byte for byte.

### 2.1 `apply --only dotclaude/s` copies exactly A and E

- [ ] **Steps:** `$CCS apply --only dotclaude/s`, then `$CCS status --long`.
- [ ] **Expected:** output as HV.2 minus "would"; afterwards `A.md` and `E.md` are gone from status; `B.md`, `D.md`, `emoji.md` still listed with unchanged labels; live `B.md` still ends with `b3 (edited here)`.
- [ ] **Check:** `E.md` in live is now the checkout's LF content (a copy, not a line-ending conversion).

### 2.2 `collect --only dotclaude/s` copies exactly B, D, emoji

- [ ] **Steps:** `$CCS collect --only dotclaude/s`, then `$CCS status --long`, then `git -C <scratch>/checkout status --short`.
- [ ] **Expected:** status: `dotclaude/s` gone entirely; git shows `s/B.md`, `s/D.md`, `s/emoji.md` as modified/added and staged or unstaged per the project's collect contract; `s/A.md` untouched.

### 2.3 Idempotence

- [ ] **Steps:** run 2.1 and 2.2 again.
- [ ] **Expected:** nothing to do, exit 0, no skips printed (there is nothing left to skip).

### 2.4 `--force` still overrides the gate (destructive, last)

- [ ] **Steps:** on a fresh scratch world, `$CCS apply --force --dry-run`.
- [ ] **Expected:** **every** file is listed as "would apply", `t/C.md` included, and **no skips print**: `--force` bypasses the two-way gate *and* the direction check, so a real `apply --force` would revert live's B, D and emoji to the checkout's older content. That is what "overwrite anyway (destructive)" in the refusal message promises, and it is the documented behaviour at 0.4.1 -- but whether `--force` should mean "ignore the gate" or "ignore everything" is an open design question. Record it if it surprises you.

## Section 3: `ccs diff <path>` (~3 min)

### 3.1 Path forms

- [ ] **Steps:** `$CCS diff s/A.md`, `$CCS diff dotclaude/s/A.md`, `$CCS diff A.md`, and on Windows `$CCS diff s\A.md`.
- [ ] **Expected:** all four resolve to the same file and print the same diff (a bare filename is fine when it is unique).

### 3.1a A bare filename that lives in two entries is refused, not guessed

- [ ] **Steps:** `$CCS diff C.md` is unique (only `t/C.md` exists) and resolves. Now create a second `C.md` under `s/` on both sides so it is ambiguous, then ask again:

  **cmd.exe**: `echo x> %TEMP%\ccs041\checkout\dotclaude\s\C.md` and `echo y> %TEMP%\ccs041\live\s\C.md` -- **PowerShell**: `Set-Content -Encoding ascii $env:TEMP\ccs041\checkout\dotclaude\s\C.md x` and `... \live\s\C.md y` -- **POSIX**: `echo x > /tmp/ccs041/checkout/dotclaude/s/C.md; echo y > /tmp/ccs041/live/s/C.md`

  then `$CCS diff C.md`.
- [ ] **Expected:** `ambiguous: 'C.md' matches 2 files -- name one of them:` followed by `dotclaude/s/C.md` and `dotclaude/t/C.md` on stderr, exit **2**, and **no diff printed**. `$CCS diff t/C.md` still works. (Found by the first sweep of this checklist: the old resolver silently took the first entry in manifest order.)

### 3.2 Emoji on a cp1252 console (Windows only -- the real thing, not the simulation)

- [ ] **Steps:** in cmd.exe, `chcp 1252`, then `%CCS% diff s/emoji.md`.
- [ ] **Expected:** the diff prints, exit 1, the unencodable character shows as `?`. **No** `UnicodeEncodeError` traceback.
- [ ] **Check:** `chcp 65001` and run again -- the character now renders.

### 3.3 Absent on one side

- [ ] **Steps:** delete live `s/B.md` (Prerequisites step 5 commands, single file), then `$CCS diff s/B.md`.
- [ ] **Expected:** header ends with `(absent in live)`, the whole file shown as removed lines, exit 1.

## Section 4: The diff tools (~5 min; needs a real terminal and a configured tool)

### 4.1 Two-way, default

- [ ] **Steps:** `$CCS diff s/A.md --difftool` (and `--difftool 2`, which is the same).
- [ ] **Expected:** your difftool opens checkout vs live; console prints `opened <tool>: checkout/dotclaude/s/A.md vs live/s/A.md`.

### 4.2 Three-way on a checkout-ahead file

- [ ] **Steps:** `$CCS diff s/A.md --difftool 3`.
- [ ] **Expected:** as HV.5. The middle pane **equals the left pane** (live == base) and the right pane has the extra line. The console says `base <sha> == live (checkout ahead)`.

### 4.3 Three-way on a live-ahead file

- [ ] **Steps:** `$CCS diff s/B.md --difftool 3`.
- [ ] **Expected:** middle pane equals the **right** pane; console says `== checkout (live ahead)`.

### 4.4 Three-way on the genuinely two-sided file

- [ ] **Steps:** `$CCS diff t/C.md --difftool 3`.
- [ ] **Expected:** three different panes; the middle is the seed (`c1..c4`, unedited); console says `neither side (both moved)`.

### 4.5 Nothing is written back

- [ ] **Steps:** in the tool, type into the output pane and save; close; then `$CCS diff t/C.md` and `git -C <scratch>/checkout status --short`.
- [ ] **Expected:** live and the checkout are byte-identical to before; only the `look-only` scratch file changed.

### 4.6 Falls back to two-way with a reason

- [ ] **Steps:** `$CCS diff s/D.md --difftool 3` (never committed).
- [ ] **Expected:** `no base could be inferred -- the path was never committed; opening the two-way view`, then the two-way tool opens.

### 4.7 `--tool` override

- [ ] **Steps:** `$CCS diff s/A.md --difftool 3 --tool vimdiff` (or any second tool you have).
- [ ] **Expected:** that tool opens instead of the configured default.

## Section 5: Against a real payload (read-only; optional, maintainers)

Only if you have a real checkout and live tree. **Dry-run only.**

- [ ] `ccs status --long` -- every `one-sided` row's evidence sha is a real commit in the checkout (`git log --oneline -- <path>` lists it) and the named side equals that commit (`git show <sha>:<path> | diff - <live file>` is empty, modulo line endings).
- [ ] `ccs apply --dry-run` and `ccs collect --dry-run` -- the union of "would" + "skipped" across both verbs equals the set of differing files; no file appears in "would" for **both** verbs.
- [ ] Pick one `two-sided` row if any exists and open it with `--difftool 3`; confirm by eye that both sides really moved away from the middle pane.

## What the automated tests DON'T cover

- A real mergetool opening three panes, and which pane is which, from a real TTY (HV.5, Section 4) -- never done before this checklist
- Colour and column rendering in cmd.exe, Windows Terminal, and POSIX terminals (1.3)
- A real cp1252 console rather than `PYTHONIOENCODING` (3.2)
- CRLF files as real editors write them, including a BOM (Section 1.4 covers CRLF only)
- The feel of `status --long` on a large payload: the base walk runs per differing file (2.5 s for 29 files on the reference machine); a payload with many two-sided files has not been measured -- see #10
- Whether `--force` should also override direction (2.4) -- a design question, not a test
- The two undecidable cases by design: a live tree that never synced from this checkout (adoption) and a file hand-reverted byte-for-byte to an old commit -- both read as "no base"; see #14

## Reporting issues found

1. Note the section and step number.
2. Capture the exact command and output (add `--no-color` if colour codes clutter it).
3. Save `git -C <scratch>/checkout log --oneline -- <path>` for the file in question -- attribution bugs are history bugs.
4. File an issue referencing this checklist and the version.
