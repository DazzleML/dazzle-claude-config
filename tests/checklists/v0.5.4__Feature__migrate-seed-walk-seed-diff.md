## What this is

The walk is **interactive and TTY-only**, which the unit tests reach only by faking `isatty` and `input`. This document exists to exercise the real binary under a real console -- which an agent can do (`winpty` on Windows, `pty`/`pexpect` on POSIX) and should -- and then to leave the judgment calls to a person: whether the prompt reads well, whether your own diff tool renders the pair, whether the keystroke rhythm feels right. `ccs migrate` performs the four beats two real machine migrations ran by hand -- keep a copy, take the payload's version, prove both copies hold the original bytes -- and the proof is the part a human silently skips (measured: on the second box the byte-compare was typed with a placeholder path in it and never completed).

## Prerequisites -- a scratch world (3 commands)

Never point these at your real config. Every command below uses explicit overrides; `ccs* =`

```
ccs --checkout-dir <S>/co --claude-dir <S>/live --user-claude <S>/user --no-fetch
```

**cmd.exe**
```cmd
set S=%TEMP%\ccs-054
mkdir %S% && cd /d %S%
git init -q -b main co && cd co && mkdir dotclaude
echo {"manifest_version":1,"territories":{"dotclaude":{"root_var":"CLAUDE_DIR","repo_dir":"dotclaude"}},"entries":[{"repo":"dotclaude/CLAUDE.md","territory":"dotclaude","target":"CLAUDE.md","strategy":"seed-if-absent"},{"repo":"dotclaude/NOTES.md","territory":"dotclaude","target":"NOTES.md","strategy":"seed-if-absent"}]} > ccs-manifest.json
echo old starter v1> dotclaude\CLAUDE.md
echo notes starter> dotclaude\NOTES.md
git add -A && git commit -qm v1
echo NEW stub v2> dotclaude\CLAUDE.md && git commit -qam v2
cd .. && mkdir live user
copy co\dotclaude\CLAUDE.md live\CLAUDE.md >nul & rem live = the OLD one? no: copy the v1 blob:
git -C co show HEAD~1:dotclaude/CLAUDE.md > live\CLAUDE.md
```

**POSIX**: same with `/tmp/ccs-054`, `printf`, and `git -C co show HEAD~1:dotclaude/CLAUDE.md > live/CLAUDE.md`.

Reset between sections: `git -C <S>/co checkout -- .`, delete `<S>/user/ccs-seed-decisions.json`, restore `live/CLAUDE.md` from `HEAD~1` as above.

## High-Value Verification (~6 minutes)

**Who drives what.** An earlier draft of this section claimed these were
human-only. That was wrong, and worth correcting in place: an agent CAN
drive the interactive walk, because a real console is available (`winpty`
ships with Git Bash; `pty`/`pexpect` on POSIX) -- and driving the real
binary under a real terminal is BETTER evidence than the unit tests, which
fake `isatty` and `input`. Each item below is tagged:

- **[agent]** -- mechanics an automated run can and should verify
- **[eyes]** -- judgment only a person can make: does the prompt read
  well, does your actual diff tool render the pair on screen, does the
  keystroke rhythm feel right. These are not assertions; they are
  opinions, which is exactly why they need a human.

### HV.1 -- the walk asks, and one keystroke answers  **[agent + eyes]**
- [ ] **Steps:** make live differ (`echo my own edit> <S>\live\CLAUDE.md`), then `ccs* seed`
- [ ] **Expected:** a numbered prompt `(1/1) CLAUDE.md`, the state in plain words, BOTH paths, the six keys; press `k`; it says `kept yours (until-changed)` and ends `done -- 1 of 1 decided`. `ccs* status` is then quiet about it.
- [ ] **Why this matters:** this is the entire ergonomic claim -- if the prompt is confusing on a real terminal, the feature failed regardless of tests.

### HV.2 -- `[d]` opens your diff tool and asks again  **[agent: mechanism | eyes: the real tool]**
- [ ] **Steps:** reset, make live differ, `ccs* seed`, press `d`
- [ ] **Expected:** your actual diff tool opens with the payload's version and yours; when you close it (or immediately, if it detaches) the SAME file is presented again -- look, then decide. Press `t` or `k` to finish.
- [ ] **Why this matters:** on the second real machine the operator hunted for `bcomp`/`bc3` by hand. ccs resolves the tool; this is where that pays off.
- [ ] **Note the tool it picked** -- if it picks a tool you did not expect, `--tool <name>` overrides, and that is worth reporting.

### HV.3 -- `[t]` migrates AND proves it, inside the walk  **[agent]**
- [ ] **Steps:** reset (live = old v1 starter), `ccs* seed`, press `t`
- [ ] **Expected:** three `verified:` lines -- your pre-migration copy intact, ccs's own backup matching byte for byte, the payload's version live -- then `migrated CLAUDE.md`. Open the kept copy: it holds your old content.
- [ ] **Why this matters:** the proof step is the one humans skip; here it is not optional.

### HV.4 -- `ccs migrate` standalone, and its dry run  **[agent]**
- [ ] **Steps:** reset; `ccs* migrate` (lists candidates); `ccs* migrate CLAUDE.md --dry-run`; then `ccs* migrate CLAUDE.md`
- [ ] **Expected:** the list names CLAUDE.md with a reason; the dry run says what it *would* do and writes nothing (check the file); the real run prints the three proofs.

### HV.5 -- Ctrl-C mid-walk changes nothing  **[agent: real SIGINT | eyes: it looks clean]**
- [ ] **Steps:** two files differing; `ccs* seed`; press Ctrl-C at the prompt
- [ ] **Expected:** clean exit, no traceback, no decisions recorded (`type <S>\user\ccs-seed-decisions.json` -- absent or unchanged).

### HV.6 -- piped mode refuses to prompt  **[agent]**
- [ ] **Steps:** `ccs* seed | more` (cmd) / `ccs* seed | cat` (POSIX)
- [ ] **Expected:** no prompt; a line telling you to run it from a terminal, or to use `ccs seed list`. Exit 1.

## What the automated tests DON'T cover

(Narrower than it looks: a tester agent under a real console covers the
mechanics of every item above. What remains is judgment.)

- Whether the prompt READS well -- layout, wording, how much text is too
  much at a decision point. An assertion can prove the words appeared;
  only a person can say they were clear
- Colors and keystroke rhythm on a real terminal
- A REAL diff tool opening (the tests stub the launcher)
- Real filesystem hazards mid-migration (a file locked by an editor, antivirus, a full disk)
- Very large starter files (both real ones were ~60 KB; nothing tests a 10 MB one)
