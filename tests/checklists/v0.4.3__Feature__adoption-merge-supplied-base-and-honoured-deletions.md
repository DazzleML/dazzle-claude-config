# Human Test Checklist: Adoption Merge -- a Supplied Base, Honoured Deletions, and `ccs base`

**Target version:** 0.4.3
**Ships with commits:** `fix: the merge validator honours deletions the base proves deliberate; without a base it asks instead of refusing` and `feat: adopt a box that forked before the payload existed -- supplied base, conflict-on-delete, ccs base, live-only accept`
**Companion automated tests:** `tests/test_honoured_deletion.py` (13), `tests/test_adoption_merge.py` (26), `tests/test_adoption_merge_tester.py` (2); mutation sweep `tests/mutation/v0.4.3__sweep__adoption-merge.md` (14 mutants: 12 killed, 2 equivalent). Tester run-01 in `results/`: SHIP.

## What this is

A machine whose `CLAUDE.md` forked before the payload existed has no common ancestor in the checkout's history. Two things stood between such a box and a safe merge:

1. The validator refused any result missing a line only one side held -- without looking at the base. So when the payload *retired* a rule on purpose, a correct three-way merge was refused every time, and nothing retired upstream could ever land through a two-sided file. Now a missing line is fine when the base holds it and the other side does not (an honoured deletion); a line one side *added* that vanished still fails. On install the tool prints what it honoured, per side, with the first line of each region -- a receipt on a right base, the alarm on a wrong one.
2. There was no way to hand the tool an ancestor from elsewhere, and a correct merge against the true ancestor silently drops every region the payload removed that the box still carries (166 lines on the real file). Now `--base-file` / `--base-from` supply one, the merge is seeded **conflict-on-delete** (those regions become reviewer hunks: 24 on the real file, 0 lost), `merge --dry-run` prints the loss table beforehand, and `--accept` writes the live file only.

Without a base the tool now shows dropped lines and asks `install it anyway? [y/N]` when a human resolved the file, instead of refusing outright.

What the automated tests cannot reach: a real merge tool showing a wrapped hunk (ours + base panes filled, theirs empty) and a repaired base pane; the console prompt for the no-base ask; line endings written by a Windows merge tool into a file destined for a Linux box; the wording of the receipt read by someone who did not write it.

## Prerequisites

1. `ccs --version` shows a 0.4.3 build; `git` on PATH; a merge tool git knows (`git mergetool --tool-help`) for the MANUAL steps.
2. Build the scratch world with the helper -- it writes a checkout (two commits, no ancestor of the live file), a live tree, and the ancestor file:

   ```
   python tests/checklists/helpers/make_scratch_v043_adopt.py <dir>
   ```

   It prints the `ccs` prefix to use. Below, `$CCS` stands for that prefix (it carries `--checkout-dir`, `--claude-dir`, `--user-claude`, `--no-color`, `--no-fetch`) and `$A` for `<dir>/ancestor.md`. Nothing below touches `~/.claude` or `~/claude`. **Reset**: delete `<dir>` and rebuild.

## High-Value Verification (~5 minutes)

### HV.1 -- `merge --dry-run` says what the merge would lose, and `lost` is 0

- [ ] **Steps:** `$CCS merge --only dotclaude/CLAUDE.md --base-file $A --dry-run`
- [ ] **Expected:** `would merge: CLAUDE.md`, then a two-row table. Row 1 `supplied ... exempt ... USABLE  conflict-on-delete on` with `lost` = `0` in both side groups; row 2 `inferred  (none)  nearest <sha> rejected ... NO BASE  rule 4`. Then `base: use file:ancestor.md -- N hunk(s) to review; 0 line(s) lost; ...` and a `conflict-on-delete:` line. Exit 0.
- [ ] **Why this matters:** this table is the oracle for every adoption; if `lost` is ever non-zero the tool is wrong, not the base.

### HV.2 -- Without a candidate, the dry run says so

- [ ] **Steps:** `$CCS merge --only dotclaude/CLAUDE.md --dry-run`
- [ ] **Expected:** `would merge: CLAUDE.md`, only the inferred row (`NO BASE  rule 4`), then `base: none usable -- supply one with --base-file / --base-from, or merge two-way (no base)`. Exit 0 (a dry run is informational).

### HV.3 -- The supplied-base merge seeds reviewer hunks, not silent drops

- [ ] **Steps:** `$CCS merge --only dotclaude/CLAUDE.md --base-file $A --no-launch`; then open `<dir>/user/merge/ccs/CLAUDE.md.merged` in an editor.
- [ ] **Expected:** first line `supplied base file:ancestor.md: CLAUDE.md -- N hunk(s) to review (... natural + ... wrapped from ... region(s) the payload removed since the base)`; `NOT INSTALLED` with `unresolved conflict markers` (expected -- you have not resolved anything). In the file: a hunk headed `<<<<<<< ours (kept verbatim; theirs deleted it since base)` whose **ours and base panes both contain `## Glossary`** and whose theirs pane is empty; the `## Editing workflow` hunk's base pane is **not empty** (it names `## Editing workflow`). The box's `## Port allocation on this box` is present outside any hunk.

### HV.4 -- `--accept` installs live only, and prints the receipt and the record line

- [ ] **Steps:** resolve the workspace file by hand (delete the marker lines; for each hunk keep what you like -- a quick choice is: keep the ours pane of the Glossary hunk, theirs pane elsewhere). Then `$CCS merge --only dotclaude/CLAUDE.md --base-file $A --no-launch --accept`. Then `git -C <dir>/checkout status --porcelain` and `git -C <dir>/checkout log --oneline -1`.
- [ ] **Expected:** `resumed CLAUDE.md -- kept your prior edits`; `merged and installed LIVE ONLY: CLAUDE.md`; `adoption merge: checkout left at HEAD; record file:ancestor.md as this box's base for CLAUDE.md`; then a `retired upstream (theirs deleted since base): N line(s) in M region(s)` block naming the sections you let go (e.g. `## Glossary` if you took theirs there). `<dir>/live/CLAUDE.md` holds your resolution; the porcelain is **empty** and HEAD is unchanged. Exit 0.
- [ ] **Why this matters:** installing a box's own sections into the shared checkout would publish them to every other machine and make them the next base -- the mechanism that deletes them on the following merge.

### HV.5 -- A retirement installs through an ordinary (inferred-base) merge

- [ ] **Steps:** rebuild the scratch world with `--history` (the helper then gives the checkout a real ancestor commit). `$CCS status --long` (expect `both moved since <sha>` for `CLAUDE.md`), then `$CCS merge --only dotclaude/CLAUDE.md --no-launch --accept`.
- [ ] **Expected:** `merged and installed: CLAUDE.md` followed by `retired upstream (theirs deleted since base): ...` naming `## Legacy notes`; `<dir>/live/CLAUDE.md` lacks that section and keeps the box's added rule. Before 0.4.3 this exact run printed `NOT INSTALLED ... line(s) present only in ours were dropped outright`.

## Section 1: The no-base ask

### 1.1 A human-resolved two-way that drops a line is asked about, on a console -- MANUAL

- [ ] **Steps:** rebuild with `--two-way` (one commit; no ancestor at all). `$CCS merge --only dotclaude/CLAUDE.md --no-launch` (seeds the workspace with ours), edit `<dir>/user/merge/ccs/CLAUDE.md.merged` so that one line only the checkout had is absent **and** the file differs from the seed (move a line), then from a real terminal: `$CCS merge --only dotclaude/CLAUDE.md --no-launch --accept`.
- [ ] **Expected:** `no base for CLAUDE.md: ccs cannot tell whether these lines were deleted on purpose or by accident --`, the dropped line(s) listed under `only in theirs, absent from your result`, then the prompt `you reviewed this file -- install it anyway? [y/N]`. Answer `n`: `NOT INSTALLED`. Re-run and answer `y`: `merged and installed: CLAUDE.md` then `with 1 line(s) dropped on your say-so (no base; you reviewed the file)`.

### 1.2 Piped stdin never accepts

- [ ] **Steps:** same state as 1.1; run with stdin redirected from an empty file (cmd: `< NUL`; PowerShell: `$null | ...`; POSIX: `< /dev/null`).
- [ ] **Expected:** no prompt; `NOT INSTALLED` with the `dropped:` failure. Exit 4.

### 1.3 An untouched seed is never asked about

- [ ] **Steps:** rebuild with `--two-way`; `$CCS merge --only dotclaude/CLAUDE.md --no-launch --accept` from a terminal, without editing anything.
- [ ] **Expected:** no prompt (the seed equals ours; you have not looked yet); `NOT INSTALLED`.

## Section 2: Supplied-base rules

### 2.1 One base, one file

- [ ] **Steps:** make a second file differ on both sides (edit `<dir>/live/other.md`), then `$CCS merge --base-file $A --no-launch` without `--only`.
- [ ] **Expected:** `ccs: --base-file/--base-from is one file's ancestor, but this run covers 2 merge candidates: ... -- scope it with --only <entry/path>`. Exit 2. With `--only dotclaude/CLAUDE.md` it proceeds.

### 2.2 `--base-from` reads out of another repository

- [ ] **Steps:** the helper creates `<dir>/home-repo` (a git repo holding `.claude/CLAUDE.md` = the ancestor). `$CCS merge --only dotclaude/CLAUDE.md --base-from <dir>/home-repo:.claude/CLAUDE.md --dry-run` and the same with `@HEAD:` inserted before the path. On Windows use the full drive path (`C:\...\home-repo:.claude/CLAUDE.md`) -- the path is whatever follows the last colon.
- [ ] **Expected:** same table as HV.1 with origin `supplied` and base `<short-sha>:.claude/CLAUDE.md`. A missing path (`...:nope.md`) reports `git show ... failed`, exit 2.

### 2.3 `--block-swap-ratio`

- [ ] **Steps:** `$CCS merge --only dotclaude/CLAUDE.md --base-file $A --dry-run --block-swap-ratio 0.4`, then `0.7`.
- [ ] **Expected:** `lost` stays 0 at both; the hunk count may differ by a few. (Reference on the real 1016-line file: 21 / 22 / 24 / 25 hunks at 0.4 / 0.5 / 0.6 / 0.7, 0 lost at every setting; below 0.40 real loss appears.)

### 2.4 The three-way look with a supplied base -- MANUAL

- [ ] **Steps:** from a real terminal with a GUI merge tool: `$CCS diff CLAUDE.md --difftool 3 --base-file $A`.
- [ ] **Expected:** your tool opens live | base `supplied` | checkout; the output pane is a scratch copy; nothing is written back (`git status --porcelain` empty; live unchanged).

### 2.5 The real adoption session in a merge tool -- MANUAL (the one that matters)

- [ ] **Steps:** `$CCS merge --only dotclaude/CLAUDE.md --base-file $A` (no `--no-launch`) from a real terminal.
- [ ] **Expected:** the tool opens on the conflict-on-delete seed. Each wrapped hunk shows the region on the LEFT (ours) and CENTER (base) and nothing on the RIGHT (theirs); resolving "take left" keeps the box's section, "take right" retires it. Save, quit, then `--accept`: the receipt names whichever you retired.
- [ ] **Line endings (if the tool runs on Windows and the file is for a Linux box):** after saving, check the workspace file has no CRLF (`git -C <dir> diff --no-index --stat` against the seed, or `file`). ccs restores the live file's own line-ending style on accept, but a CRLF workspace file on an LF box would make every line read as changed in the next `status`. Record what your tool did.

## Section 3: Against a real forked box (read-only rehearsal) -- MANUAL

- [ ] Mirror the box's `~/.claude` to scratch (never run ccs against the production tree itself). Point `--claude-dir` at the mirror, `--checkout-dir` at a scratch clone of the payload at the box's current HEAD. `ccs merge --only dotclaude/CLAUDE.md --base-from <seeding-machine-home-repo>@<sha>:.claude/CLAUDE.md --dry-run`.
- [ ] **Expected:** `lost` 0; a hunk count you are prepared to review (reference: 24); the `retired` / `ours-del` first lines are sections you recognise as the other platform's or as genuinely retired. If you see one of **this box's own** headings under `retired upstream`, the base is wrong -- stop.
