# Human Test Checklist: explanations as packaged data, and the `--explain` index

**Target version:** 0.5.12
**Ships with commit:** `refactor: settings explanations become packaged data (v0.5.12)`
**Companion automated tests:** 538 total (was 517). For this surface: `tests/test_explanations_ship.py` (14), `tests/test_setup_update.py` (50), `tests/test_config_keys_table.py` (15), `tests/test_setup_doctor.py` (21), `tests/test_remote_awareness.py` (19).

## What this is

The words that `ccs setup update --explain` prints used to live in Python source. They now live in a JSON file shipped inside the installed package, and `docs/configuration.md` is generated from that same file. This checklist exists because **the most important failure mode of that change is invisible in a source checkout**: with the packaging declaration missing or misspelt, `--explain` works perfectly in this repo and answers with nothing after `pip install`. No automated test run from the source tree can see that. Section 1 installs a real wheel into a throwaway environment and asks it a question, and it is the reason this document exists.

The second reason is that `--explain` now behaves differently depending on whether a human is at a terminal, and pytest's captured output is never a terminal. Every branch in Section 2 is unreachable by the test suite.

Sections 6 and 7 were added after the first draft and cover work that lands in the same release: `ccs doctor` now reports the state of your config file rather than only whether it parses, and `ccs status` no longer calls a checkout "clean" while it holds commits nobody else has.

Run this together with the two checklists named in **Related** below -- they were written to be run as one pass over the whole configuration surface.

## Prerequisites

1. **Python 3.10+**, `git` on PATH, and a working `python -m build` (`pip install build`).
2. **Never run against your real config -- and `--user-claude` alone does NOT achieve that.** ccs resolves three locations independently, and any one you omit falls back to your real machine:

   | Flag | Omitting it falls back to |
   |---|---|
   | `--user-claude <scratch>/user` | your real `~/claude` |
   | `--claude-dir <scratch>/live` | your real `~/.claude` |
   | `--checkout-dir <scratch>/co` | your real payload checkout |

   **Pass all three on every `ccs` invocation in this document**, including read-only verbs like `doctor` and `status`, and including steps whose own text shows fewer. This instruction previously named only `--user-claude`; a run following it exactly reached the operator's real checkout and real `~/.claude` and fetched from a real GitHub remote. Nothing was damaged, but the assurance was worse than no assurance, because it read as a guarantee. Where a step below writes `ccs ... --user-claude <scratch>/user`, read it as shorthand for all three.
3. **Never point ccs at a production box.** In this project's fleet, `X:` is read-only and off limits; do not use it as a scratch path or a checkout.
4. **The wheel install uses a throwaway virtual environment**, never your working environment. Section 1 creates and deletes it.
5. **A real terminal is required** for Section 2. Running it inside an IDE's output pane, a CI job, or any captured console will silently exercise the redirected path instead and every result will be a false pass.

### Scratch setup

**cmd.exe**
```cmd
set CCSTEST=%TEMP%\ccs-0512
if exist "%CCSTEST%" rd /s /q "%CCSTEST%"
mkdir "%CCSTEST%\user"
```

**PowerShell**
```powershell
$env:CCSTEST = "$env:TEMP\ccs-0512"
if (Test-Path $env:CCSTEST) { Remove-Item -Recurse -Force $env:CCSTEST }
New-Item -ItemType Directory -Force "$env:CCSTEST\user" | Out-Null
```

**POSIX**
```bash
export CCSTEST=/tmp/ccs-0512
rm -rf "$CCSTEST"
mkdir -p "$CCSTEST/user"
```

### Resetting between sections

Delete and recreate the scratch directory using the block above. Nothing in this checklist writes outside it, except Section 3 which temporarily edits files **inside the repo** and tells you exactly how to put them back.

### If any step builds a git fixture

No section here requires one. If you add one while exploring: every git command must carry `-C <scratch path>` so it can never land in a real repository, and every commit or tag must carry `-c user.email=test@example.com -c user.name=Test -c commit.gpgsign=false -c tag.gpgsign=false`. This machine has `commit.gpgsign = true` globally, and a bare `git commit` fires an interactive GPG dialog at whoever is sitting at the keyboard. Never change global git config to work around it.

## High-Value Verification (~5 minutes)

If you only have five minutes, run these six.

### HV.1 -- The explanations survive a real install

Validates: the packaging declaration actually ships the data file.

- [ ] **Steps:**
  1. Build a wheel and install it into a throwaway environment (full commands in 1.1).
  2. From that environment, in a directory that is **not** the repo, run:
     `ccs --user-claude <scratch>/user setup update --explain sync_removals`
- [ ] **Expected:** several sentences of prose about retired files, ending with the line naming `CCS_SYNC_REMOVALS`.
- [ ] **Why this matters:** if this prints an "explanation unavailable" line instead, the data file did not ship, and every installed user gets a documentation command that documents nothing. This is the single check the whole checklist exists for.

### HV.2 -- A terminal gets an index, not a wall

Validates: the interactive shape of the change.

- [ ] **Steps:** at a **real terminal**, run `ccs --user-claude <scratch>/user setup update --explain`
- [ ] **Expected:** about 15 lines -- a count, a URL, one line per setting, a hint naming `--explain <name>`, then the question `Print all 11 in full here? [y/N]`. Not 80 lines.
- [ ] **Why this matters:** the old behaviour scrolled the top of its own output off the screen.

### HV.3 -- A pipe gets everything and is never asked

Validates: the branch that a Windows `isatty()` gets wrong.

- [ ] **Steps:** `ccs --user-claude <scratch>/user setup update --explain > "<scratch>/all.txt"` then count the lines.
- [ ] **Expected:** 80 lines of full prose. **No prompt appears, and the command returns immediately.**
- [ ] **Why this matters:** a prompt here hangs a script forever on a question nothing can answer. This exact failure was observed during development.

### HV.4 -- One setting still answers directly

- [ ] **Steps:** `ccs --user-claude <scratch>/user setup update --explain auto_pull`
- [ ] **Expected:** the full text for that setting, no prompt, no URL, exit code 0.
- [ ] **Why this matters:** this is the form people actually reach for, and it must not have acquired a question.

### HV.5 -- Truncated summaries are readable on a Windows console

- [ ] **Steps:** in **cmd.exe**, run `chcp 437` then the bare `--explain`.
- [ ] **Expected:** truncated lines end in three ASCII periods `...`. No `?`, no box, no replacement glyph.
- [ ] **Why this matters:** a single-character ellipsis was a real defect here, found by looking at output rather than at code.

### HV.6 -- Losing the prose must not change what ccs does

- [ ] **Steps:** rename `settings-explanations.json` inside the installed package, then run `ccs doctor` and `ccs setup update --dry-run`, both with all three scratch overrides.
- [ ] **Expected:** doctor **warns**, naming the reason and the docs URL. `setup update --dry-run` still reports the same 11 settings with the same defaults.
- [ ] **Why this matters:** an unexplained setting is an annoyance; a setting that lost its default is a machine quietly behaving differently from the one beside it. Restore the file afterwards.

## Section 1: The data file actually ships (~10 min)

### 1.1 Build a wheel and install it somewhere disposable

- [ ] **Steps:**

  **cmd.exe**
  ```cmd
  cd /d C:\path\to\dazzle-claude-config-tool
  python -m build --wheel --outdir "%CCSTEST%\dist"
  python -m venv "%CCSTEST%\venv"
  "%CCSTEST%\venv\Scripts\python.exe" -m pip install --quiet "%CCSTEST%\dist\dazzle_claude_config-0.5.12-py3-none-any.whl"
  ```

  **PowerShell**
  ```powershell
  Set-Location C:\path\to\dazzle-claude-config-tool
  python -m build --wheel --outdir "$env:CCSTEST\dist"
  python -m venv "$env:CCSTEST\venv"
  & "$env:CCSTEST\venv\Scripts\python.exe" -m pip install --quiet (Get-ChildItem "$env:CCSTEST\dist\*.whl").FullName
  ```

  **POSIX**
  ```bash
  cd /path/to/dazzle-claude-config-tool
  python -m build --wheel --outdir "$CCSTEST/dist"
  python -m venv "$CCSTEST/venv"
  "$CCSTEST/venv/bin/python" -m pip install --quiet "$CCSTEST"/dist/*.whl
  ```

- [ ] **Expected:** a wheel is built and installs without error.
- [ ] **Check:** the repo-side guard agrees --
  `python scripts/check-wheel-data.py "<scratch>/dist/"*.whl` prints `ok: ... ships dazzle_claude_config/settings-explanations.json`.

### 1.2 Ask the INSTALLED copy, from outside the repo

This is the step that cannot be faked from a checkout. **Change directory out of the repo first** -- otherwise Python may import the local package and tell you what you wanted to hear.

- [ ] **Steps:**

  **cmd.exe**
  ```cmd
  cd /d %TEMP%
  "%CCSTEST%\venv\Scripts\ccs.exe" --user-claude "%CCSTEST%\user" setup update --explain sync_removals
  ```

  **PowerShell**
  ```powershell
  Set-Location $env:TEMP
  & "$env:CCSTEST\venv\Scripts\ccs.exe" --user-claude "$env:CCSTEST\user" setup update --explain sync_removals
  ```

  **POSIX**
  ```bash
  cd /tmp
  "$CCSTEST/venv/bin/ccs" --user-claude "$CCSTEST/user" setup update --explain sync_removals
  ```

- [ ] **Expected:** the full explanation, ending with the line naming `CCS_SYNC_REMOVALS`.
- [ ] **Expected NOT:** any line containing `explanation unavailable`. That means the file did not ship.

### 1.3 The installed copy passes its own health check

- [ ] **Steps:** from the same installed environment, run `ccs doctor` with **all three** overrides: `--checkout-dir <scratch>/co --claude-dir <scratch>/live --user-claude <scratch>/user`. (`doctor` consults all three; naming only one sends it at your real machine.)
- [ ] **Expected:** a line reading `settings explained (11)`.

### 1.4 Confirm it is genuinely the installed copy talking

- [ ] **Steps:** run
  `"<venv python>" -c "import dazzle_claude_config, sys; print(dazzle_claude_config.__file__)"`
- [ ] **Expected:** a path inside the throwaway venv's `site-packages`, **not** inside your repo. If it points at the repo, Section 1's result proves nothing -- fix the working directory and run it again.

## Section 2: `--explain` at a terminal, and away from one (~10 min)

**Every step in this section requires a real console.** These branches are invisible to the test suite by construction.

### 2.1 The index

- [ ] **Steps:** `ccs --user-claude <scratch>/user setup update --explain`
- [ ] **Expected:**
  - A first line naming the number of settings and pointing at a full reference.
  - The documentation URL on its own line.
  - One line per setting: name, default, and the first sentence of its explanation, in aligned columns.
  - A hint naming `ccs setup update --explain <name>`.
  - The question `Print all 11 in full here? [y/N]`.
- [ ] **Check by eye:** do the three columns line up? Does anything wrap past the right edge at 80 columns? Narrow your window to 80 and run it again.
- [ ] **Check the judgement, not just the format:** is the first sentence of each setting actually enough to tell you whether it is the one you want? If any line is uninformative, that is a finding worth reporting even though nothing is broken.

### 2.2 Answering yes

- [ ] **Steps:** run the bare `--explain`, type `y`, Enter.
- [ ] **Expected:** all 11 settings in full, each with default, valid values where it has them, the prose, and its environment variable.

### 2.3 Answering no, and answering nothing

- [ ] **Steps:** run it three times, answering `n`, then bare Enter, then `banana`.
- [ ] **Expected:** all three exit without printing the full text, exit code 0. Only `y` or `yes` should print.

### 2.4 Ctrl-C at the prompt

- [ ] **Steps:** run the bare `--explain` and press Ctrl-C at the question.
- [ ] **Expected:** returns cleanly with exit code 0 and no traceback. Declining a question is not an error.
- [ ] **Check exit code:** `echo %ERRORLEVEL%` (cmd) / `$LASTEXITCODE` (PowerShell) / `echo $?` (POSIX).

### 2.5 Redirected

- [ ] **Steps:**

  **cmd.exe**
  ```cmd
  ccs --user-claude "%CCSTEST%\user" setup update --explain > "%CCSTEST%\all.txt"
  type "%CCSTEST%\all.txt" | find /c /v ""
  ```

  **PowerShell**
  ```powershell
  ccs --user-claude "$env:CCSTEST\user" setup update --explain > "$env:CCSTEST\all.txt"
  (Get-Content "$env:CCSTEST\all.txt" | Measure-Object -Line).Lines
  ```

  **POSIX**
  ```bash
  ccs --user-claude "$CCSTEST/user" setup update --explain > "$CCSTEST/all.txt"
  wc -l < "$CCSTEST/all.txt"
  ```

- [ ] **Expected:** 80 lines. The command returns immediately with **no prompt**, and the file contains full prose, not the index.

### 2.6 Piped into a pager

- [ ] **Steps:** `ccs --user-claude <scratch>/user setup update --explain | more`
- [ ] **Expected:** full text, paged. **No question appears.** If the command appears to hang, that is the defect this branch exists to prevent -- record it.

### 2.7 The opt-out environment variable

- [ ] **Steps** (at a terminal):

  **cmd.exe**: `set CCS_INTERACTIVE=0` then the bare `--explain`, then `set CCS_INTERACTIVE=`
  **PowerShell**: `$env:CCS_INTERACTIVE = "0"` then the bare `--explain`, then `Remove-Item Env:\CCS_INTERACTIVE`
  **POSIX**: `CCS_INTERACTIVE=0 ccs --user-claude "$CCSTEST/user" setup update --explain`

- [ ] **Expected:** the index prints and **no question is asked**. Exit code 0.
- [ ] **Also try** the value `" 0 "` with surrounding spaces -- it must behave identically. A shell script or CI template producing a padded value is ordinary, and a prompt appearing there would hang the run.

### 2.8 One setting, and a setting that does not exist

- [ ] **Steps:** `--explain auto_pull`, then `--explain nonsense`.
- [ ] **Expected:** the first prints full text with no prompt and no URL. The second prints `no such setting: nonsense`, lists the known settings, and exits non-zero.

### 2.9 Codepage 437 (cmd.exe only) -- **the one mocks cannot reach**

- [ ] **Steps:**
  ```cmd
  chcp 437
  ccs --user-claude "%CCSTEST%\user" setup update --explain
  ```
- [ ] **Expected:** every truncated summary ends in three ASCII periods. No `?`, no `�`, no box glyph, anywhere in the output.
- [ ] **Also check:** run the same under `chcp 65001` (UTF-8) and confirm it is unchanged. Output should not depend on codepage at all.

### 2.10 `--explain` still writes nothing and needs nothing

- [ ] **Steps:** point `--user-claude` at an **empty** directory with no config file, and run `--explain sync_removals`.
- [ ] **Expected:** it answers normally.
- [ ] **Check:** no `ccs-config.json` was created. A question must not have side effects, and a machine with nothing set up yet must still be able to ask.

## Section 3: The generated documentation page (~10 min)

This section edits files **inside the repo**. Step 3.4 puts them back; do not skip it.

### 3.1 The page is current

- [ ] **Steps:** `python scripts/gen-config-docs.py --check`
- [ ] **Expected:** `docs/configuration.md is current (11 settings)`, exit code 0.

### 3.2 A stale page is caught -- by the script AND by the suite

- [ ] **Steps:**
  1. Edit `dazzle_claude_config/settings-explanations.json` and change a word inside any setting's text.
  2. `python scripts/gen-config-docs.py --check`
  3. `python -m pytest tests/test_explanations_ship.py -q`
- [ ] **Expected:** step 2 exits 1 and names the regeneration command. Step 3 goes **red**.
- [ ] **Why this matters:** this is what makes "generated" a guarantee rather than a habit. If the suite stays green here, the page can silently drift and the whole argument for generating it collapses.

### 3.3 Regenerating fixes it

- [ ] **Steps:** `python scripts/gen-config-docs.py`, then re-run `--check` and the test file.
- [ ] **Expected:** both green. The only diff in `docs/configuration.md` is the word you changed.

### 3.4 Reset

- [ ] **Steps:** revert your edit to the JSON, regenerate, and confirm `git status --short` shows neither file modified.

### 3.5 Read the page as a reader would

- [ ] **Steps:** open `docs/configuration.md` in a Markdown preview, and ideally on GitHub after the branch is pushed.
- [ ] **Check:**
  - The summary table renders as a table, and each setting name links to its own section further down. **Click one.** Generated anchors are the classic thing that looks right in source and does not work in the browser.
  - Every setting has a section with its default, environment variable, and valid values where it has them.
  - No paragraph is hard-wrapped mid-sentence.
  - The generated-file warning at the top is visible to someone about to hand-edit it.
- [ ] **Check the judgement:** would you rather read this page or run `--explain`? If the page is worse than the terminal output, say so -- that is a finding.

## Section 4: doctor, and losing the prose (~5 min)

Do this against the **installed** copy from Section 1 if you can; that is where the failure would really happen.

### 4.1 Healthy

- [ ] **Steps:** `ccs doctor --checkout-dir <scratch>/co --claude-dir <scratch>/live --user-claude <scratch>/user`
- [ ] **Expected:** `settings explained (11)`.

### 4.2 The file is gone

- [ ] **Steps:** rename `settings-explanations.json` in the installed package to `.json.bak`, then run `ccs doctor` again (all three overrides).
- [ ] **Expected:** a **warning** naming what is missing and pointing at the documentation URL. Not a crash, not a traceback.

### 4.3 ccs still works correctly without it -- the load-bearing check

- [ ] **Steps:** with the file still renamed, run:
  1. `ccs setup update --dry-run --user-claude <fresh empty scratch>`
  2. `ccs setup update --explain sync_removals`
- [ ] **Expected:**
  1. Reports the same **11** settings with the same defaults. Behaviour is unaffected.
  2. Prints the setting's name, default and valid values, then an "explanation unavailable" line pointing at the docs URL -- **not** a blank space, and not the setting's own name echoed back as its meaning.
- [ ] **Why this matters:** this is the invariant the whole design rests on. Losing the prose file must cost words only.

### 4.4 A corrupted file behaves the same way

- [ ] **Steps:** restore the name but replace the contents with `{ not json`, then run `ccs doctor` (all three overrides).
- [ ] **Expected:** a warning saying it is not valid JSON. ccs still runs.

### 4.5 Reset

- [ ] **Steps:** restore the original file (reinstall the wheel if easier) and confirm 4.1 passes again.

## Section 6: doctor reports the state of your config file (~5 min)

New in this pass. Before it, doctor asked one question about the config -- does it parse? A file can parse perfectly and still lack five settings this version knows, which is the whole reason issue #32 exists.

### 6.1 A config that predates settings this version knows

- [ ] **Steps:** write a config holding only six of the eleven settings, then run doctor:

  **cmd.exe / PowerShell / POSIX** (cross-shell, uses python only):
  ```
  python -c "import json,pathlib,sys; pathlib.Path(sys.argv[1]).write_text(json.dumps({'on_divergence':'prompt','difftool':None,'interactive':True,'status_detail':'auto','status_max_lines':30,'fetch':True},indent=2),encoding='utf-8')" <scratch>/user/ccs-config.json
  ccs --checkout-dir <scratch>/co --claude-dir <scratch>/live --user-claude <scratch>/user --no-fetch doctor
  ```

- [ ] **Expected:** a `[WARN]` line naming **all five** missing settings by name -- `ai_merge_command`, `auto_pull`, `fetch_timeout`, `require_current`, `sync_removals` -- plus `ccs setup update` and the reassurance that it changes nothing you set.
- [ ] **Check the judgement:** `sync_removals` moves files. Reading this line and nothing else, would you understand that a setting you have never seen is currently governing whether your files get staged into a backup directory? If not, say what is missing.

### 6.2 A config with nothing missing

- [ ] **Steps:** run `ccs setup update` against the same scratch, then doctor again.
- [ ] **Expected:** `[ OK ] user config ccs-config.json (11 settings, none missing)`. The word "predates" must not appear.

### 6.3 No config file at all

- [ ] **Steps:** point `--user-claude` at an empty directory and run doctor.
- [ ] **Expected:** `[ OK ]`, **not** `[WARN]` -- running on defaults is the designed state and behaves safely. It still says so, and names `ccs setup update`.
- [ ] **Why this distinction matters:** flagging every fresh machine yellow for doing nothing wrong is how people learn to skim past doctor's output.

### 6.4 A key this version does not know

- [ ] **Steps:** add `"from_a_newer_ccs": true` to the config, run doctor.
- [ ] **Expected:** reported, described as left alone, and the key is **still in the file afterwards**. Check the file.

### 6.5 A broken config, and a config that is not an object

- [ ] **Steps:** write `{oops` and run doctor; then write `[1, 2, 3]` and run doctor.
- [ ] **Expected:** the first says **not valid JSON**; the second says **not a JSON object**. They must not say the same thing -- `[1,2,3]` is valid JSON and would send someone hunting for a syntax error that is not there.
- [ ] **Expected NOT:** the word `JSONDecodeError` anywhere. That is the parser's word, not a person's.

### 6.6 doctor writes nothing

- [ ] **Steps:** hash every file in the scratch world, run doctor, hash again.
- [ ] **Expected:** identical. doctor is read-only by contract because it runs on read-only-policy boxes.

## Section 7: the status summary and the remote (~5 min)

Requires a scratch fixture with a real upstream. Every git command here carries `-C <scratch>` and `-c commit.gpgsign=false -c tag.gpgsign=false -c user.email=test@example.com -c user.name=Test`.

### 7.1 A checkout that is AHEAD is not called "clean"

- [ ] **Steps:** commit in the scratch checkout without pushing, make live match it, run `ccs status`.
- [ ] **Expected:** the final line does **not** say `status: clean`. It says live matches the checkout, that N commits here are not on the upstream yet, and names `ccs git push`.
- [ ] **Why this matters:** "clean" previously appeared while a commit existed on exactly one machine. Behind means you get it on the next pull; ahead means a dead disk takes it.

### 7.2 One commit versus several

- [ ] **Expected:** `1 commit here is not on ...` and `2 commits here are not on ...`. Read both. Four separate plural defects shipped in this release before being caught by eye.

### 7.3 A diverged checkout is not told to fast-forward

- [ ] **Steps:** advance both the upstream and the checkout, run `ccs status`.
- [ ] **Expected:** the word **diverged**, and **no** recommendation of `ccs status --pull` -- a fast-forward cannot resolve a divergence, so recommending it would send you to a command that must refuse.

### 7.4 Nothing pending is still one green line

- [ ] **Steps:** with everything in sync and matching, run `ccs status`.
- [ ] **Expected:** `status: clean`, exit 0. The three checks above must not have made the ordinary case noisy.

## What the automated tests DON'T cover

- **Whether the file is in the wheel.** Tests run from the source tree, where the file is on disk regardless of packaging. Only Section 1 answers this, and it is the reason this checklist exists.
- **Anything TTY-dependent.** Captured test output is never a console, so the index, the prompt, the yes/no answers and Ctrl-C are all reached in tests only by injecting a fake console detector. Sections 2.1-2.7 exercise the real thing.
- **Codepage rendering.** A test can assert a string is encodable; only a person can see whether cmd.exe on codepage 437 draws it as intended (2.9).
- **Whether the rendered Markdown works in a browser.** A test compares generated text to expected text; it cannot click an anchor link (3.5).
- **Whether the writing is any good.** Nothing automated can tell you a one-line summary is uninformative or that the page is harder to read than the terminal. 2.1 and 3.5 ask for that judgement deliberately.
- **The pure-function edges the real data never reaches.** The mutation sweep above found four behaviours that were unconstrained while appearing covered, precisely because every assertion about them went through rendered output that the eleven real explanations never pushed to its edges. Tests were added; the general lesson is that "it looked right" is not coverage.
